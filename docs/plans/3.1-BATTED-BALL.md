## 已确认功能与流程

| 内容 | 3.1 范围 |
| --- | --- |
| 球型记录 | 单选地滚、强力地滚、平飞、高飞、内野小飞、触击、没有看清；不由球型自动推断安打、出局或统计结果 |
| 方向与落点 | 记录大致击球去向，区分点选位置、仅选区域和位置未知；保留场地轮廓、方向线、落点与球型标记，图上去掉位置名称 |
| 现有流程衔接 | 选完球型／去向后接回现有结果、守备、跑者及得分判定；已选信息沿用，随本球一次保存，取消草稿不留独立记录，不增加重复结果／确认流程 |
| 打者查看入口 | 点击当前打者打开本场／年度打击表现与击球图，覆盖本队和对方；打者栏保留棒次、背号和姓名，不添加「查看表现」提示 |
| 本场与年度汇总 | 本场只计已完成打席；年度只汇总实际记录到且有权查看的比赛，按稳定球员身份及最新正式修订去重，不按同名／同背号合并 |
| 常用局面入口 | 参考「V2 局面记录优化」，在击球面板第一屏提供常用／全部击球入口；完整项数、顺序与展开布局在实施前细化，已有一垒安打、接杀、滚地出局、双杀衔接方案可复用 |

既有 [交互提案与样例](../design/3.0/BATTED-BALL-PROPOSAL.md) 保留为设计输入；文件所在的 3.0 目录是历史来源，不代表加入 3.0 交付。功能版本已确定为 3.1，具体布局及完整常用目录继续细化，不重做现有比分、球场和投球按钮。

普通界外球沿用现有入口；界外接杀可记录界外区域，本垒打区分方向与实际结果。普通棒球、教练投手与成人慢垒沿用各自规则，观察字段不能绕过触击等限制。球型和位置允许分别未知，旧比赛缺失资料保持未知，不凭文字或结果补造位置。

## 数据、权限与兼容

观察字段与本球、打席、球员身份和比赛修订绑定，接入本机保存、重启恢复、撤销／重做、历史纠错、备份／恢复及共享比赛同步。对旧格式和缺失字段明确兼容；新格式遇到不支持的客户端时遵守现有协议能力判断，避免旧端写回丢失新字段。

本场／年度表现区分统计覆盖数量与有位置的击球数量。三种比赛模式分别筛选或清晰标识；历史更正、撤销与球员对应变化后，统计和图同步更新。对方年度只代表已记录范围，不能宣称完整年度成绩。

球队角色、正式记分权、同步与交接、历史观看授权沿用 3.0。只读查看不授予修改能力，打者年度入口不得暴露其他私有比赛。网页和报告继续使用现有能力；同步与导出需保证新资料保存一致，是否新增网页／报告击球图展示在范围细化时明确，不自动扩大到完整年度公开门户。

## 规划完成后的任务与聊天安排

从 3.1 起，先完成版本规划，明确功能范围、流程和验收边界，再按完整任务拆分开发聊天。当前规划仍有布局、常用目录及网页／报告展示范围待细化，尚未进入最终拆分。

- 保留一个规划与进度聊天，负责已确认要求、任务依赖、完成状态和最终整体验收；具体开发由用户在各任务聊天中依次开展。
- 拆分时提供每项任务的建议聊天名称、目标与范围、前置依赖、相关文件、验收要求及可直接复制的新聊天起始说明。任务数量按实际依赖确定，沿用 BB01–BB08 编号以便追踪。
- 同一功能的实现、修复和验证留在同一个任务聊天；完成后再转入下一项。各聊天沿用同一项目目录和当前开发基线，按任务顺序实施。
- 每项任务结束，将已完成、未完成、关键决定、相关文件和验证结果写回项目文档；下一项读取简短交接及相关内容，无需复制完整聊天历史。
- 任务清单附模型建议：日常实现、常规修复与发布准备建议 GPT-6.1 Sol；复杂设计与疑难问题建议 GPT-6 Astra，由用户在对应聊天中选择。
