Android 首版原建议以 3.0 稳定功能及协议为基线，包括现有三种比赛模式、本机离线记分与球队协作；恢复安排时按届时 iOS 发布基线核对具体页面和能力清单。Android 与 iOS 不需要版本号相同才能协作，兼容性由服务协议和客户端能力决定。

3.0 已定义稳定的球队、成员、设备、球员和比赛 ID，以及授权规则、数据格式、错误码、版本兼容、幂等操作、同步修订和记分权交接。协议不以 Apple 账号、Keychain 或 Core Data 的实现细节作为身份和数据格式。现有平台无关样例与基准数据可供后续复用；真实 Android 跨平台联调随客户端开发一起暂缓。

## Android 实现建议

建议采用 Kotlin、Jetpack Compose 与 Room，单独实现 Android 界面、本地存储、文件分享和凭证安全存储；技术选型与最低系统、目标机型在实施前定稿。沿用产品流程、品牌资源、记分规则及基准比赛案例，复用已实现的服务接口。

本机记分继续离线可用；共享数据通过服务器授权与同步。成员在不同系统之间换设备，仍须邀请、配对或恢复授权，不能靠复制备份获得权限。备份互导需要明确格式兼容与数据映射；两端本地数据库不直接互换。

## APK 分发与更新

规划通过 `baseballmaster.cc` 的下载页面提供签名 Release APK、版本信息、更新说明和安装指引。应用内检查更新后引导用户下载，并经系统确认覆盖安装；安装与更新在目标系统和品牌设备上验证。

从首次正式分发起固定包名并妥善管理签名密钥，每次发布递增版本编号。密钥及密码不进入 Git 或公开目录，须安全备份。覆盖升级保留比赛资料，数据结构变化提供迁移及失败恢复；不以卸载重装作为正常更新流程。

正式分发前按当时的目标地区和设备核对开发者验证要求、安装限制及下载兼容性。不上应用市场不自动代表没有开发者验证要求。具体发布政策不在本规划中写成永久承诺。

## 验收重点

- iOS 与 Android 加入同一球队、关联同一成员时，角色和可见范围一致；不同球队权限隔离。
- 同一场比赛始终只有当前获授权设备提交正式记录；两端正常交接及失联接管均不双写。
- 降级、移除成员、撤销设备或观看授权后，两端 API 均拒绝越权；离线资料按 3.0 的边界处理。
- 同一组基准比赛在两端产生一致的比分、球员归属和技术统计，报告与直播内容一致。
- 断网、进程终止、重启及旧备份恢复不丢失已保存的本机记录，不恢复已撤销权限。
- 新版 Android 与受支持的 iOS 3.0 客户端可协作；遇到不支持的数据语义时拒绝写回并清晰提示。
- APK 首次安装、覆盖升级、数据库迁移及失败恢复通过；无须卸载即可正常更新。
