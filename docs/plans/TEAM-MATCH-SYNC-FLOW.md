# 球队比赛同步：问题核查与流程优化提案

记录日期：2026-11-02（北京时间）  
状态：核查与设计记录；“首页创建并启动记录、共享球队只查看和管理”的入口原则已由用户确认，其余方案细节待评审；未指定发布版本，本轮不实施业务代码。  
核查基线：main `4b93361c8ce01bb1f76b23bb901a5ef177be8286`。

## 1. 本次需求与证据边界

用户要求先核实，再设计优化，原始反馈为：

1. 本机记录，同步共享球队，没有问题。
2. 开始设置比赛，选择共享球队，记录完毕后，没有也无法共享给球队。
3. 共享比赛的设置入口太多：建立比赛时可以设置，在共享球队内也可以设置，令人疑惑。

用户随后补充第二条的完整现象：**用第二种方式建立并记录比赛后，本队/本机球队与共享球队两个范围都看不到比赛统计，admin 后台仍显示比赛未开始。**因此本条必须作为“结束状态、统计归属和云端更新不一致”的问题记录，不能缩减成不会选择共享入口或没有另选共享目标。用户明确要求本轮先不改任何代码。

用户进一步确认：**首页“比赛 → 开始新比赛”统一创建本机比赛或共享球队比赛；设置完成后，两类比赛都从首页开始/继续记录。共享球队页面只用于查看和管理，不提供新建比赛、赛前启动或开始/继续记分入口。**此前“共享球队页面仍可作为创建或记分的快捷入口”的建议不再采用。

本次核查依据固定基线的 iOS 源码、已有测试内容及用户在 10 月 31 日提供的截图。没有取得手机完整备份、真机网络日志或生产服务器 SSH 接入；没有在本轮运行 iOS App 或重跑 XCTest。下文“代码确认”表示可以从分支条件和数据路径确定行为，不表示完成真机重现。

截至记录时，[PR #33](https://github.com/chending0418-ship-it/baseballMaster/pull/33) 仍为未合并的草稿，包含此前排查时的开赛入口、补传及错误提示修正。它不属于当前 main，也不代表用户手机已更新。本提案独立记录完整产品流程，不把该草稿视为已经发布或已通过验收的方案。

## 2. 三条反馈核查结论

| 用户反馈 | 结论 | 具体范围 |
| --- | --- | --- |
| 本机记录后共享球队正常 | 首次共享能力有代码和既有测试支持，用户也报告此路径可用；“完全没有问题”的表述应收窄 | 支持将本机比赛首次发布为球队副本，也支持历史比赛导入。但当前规则明确保留本机原件与独立球队副本，本机后续修改不会自动更新球队副本。 |
| 建赛选择共享球队，记完后两边都无统计、后台仍未开始，也无法补共享 | 完整现象有用户反馈和前述截图支持；代码存在可解释这些症状的缺口，真实记录的具体触发条件仍待核对 | 需同时核对本机完成状态/球队 ID、统计筛选、云端状态与修订。代码确认共享名单选择和共享目标独立，且已有副本会阻止重复发布；这些是候选原因，不能据此断言用户漏选了共享目标。 |
| 共享入口多且令人疑惑 | 代码确认存在多个入口，并存在文案与职责重叠 | 建赛的“队内共享”、本机比赛详情的共享、共享球队比赛列表的“共享本机比赛”、管理员的“导入历史比赛”并存。另有“使用共享名单开始比赛”，名称和所在位置容易被理解为创建球队比赛，实际仍默认保存本机。 |

因此问题不限于网络或入口数量：当前产品同时存在名单/归属语义混淆、原件/副本更新断开，以及本机记录可能落不进任何可选统计范围的代码风险。必须以“单场已结束有比分 → 对应本机范围可找到记录 → 同一云端比赛进入已结束并更新比分 → 球队正式统计纳入”为完整验收链。网络连接失败仍是独立待查事项，不能用流程结论解释所有连接报错。

### 两种代码路径与完整症状

以下路径用于解释实现及建立后续复现用例，不是对用户实际操作的替代判断。尤其“本机/共享统计都没有，后台未开始”的完整反馈不能只靠路径 A 解释。

**路径 A：只选择共享名单。** 新建 → “本队”选择 WBC U12 的共享球队 → 没有另选共享目标 → 开赛/完赛。代码预期是本机记录，不会自动上传。用户对“已经选择共享球队”的理解与实现不一致。

**路径 B：创建时已经上传。** 建赛/安排赛程 → 另选“队内共享”并上传 → 从首页打开本机赛程/比赛继续记分 → 完赛后重新选择共享球队。首次快照可能是 0:0，后续修改落在本机原件；已有副本挡住再次发布，用户既无法补传，也不知道该去编辑哪份记录。

用户截图中，本机单场显示 WBC U12 对 TOP 为 14:1，云端对应比赛仍为 0:0，并出现“查看已共享的比赛”；两个统计范围均为 0 场，用户补充 admin 仍显示未开始。用户已确认从首页“即将进行”进入。路径 B 与云端初始快照不更新相符，但它本身还不足以解释本机统计缺失；后者还需核对 E09 的归属与筛选条件。

真实记录核查应逐场对照：本机 ID、`ourTeamID`、`sharedTeamID`/`sharedGameID`、状态/`isFinal`、比赛年度与日期、来源关联、云端修订及上传队列。现无完整备份和授权的云端记录，尚不能确定是哪几个条件同时命中，也不能认定比赛已丢失或自动覆盖云端。

## 4. 建议的目标流程

用户确认的原则：**首页“比赛”是创建、赛前设置和启动/继续记分的统一入口；共享球队只负责查看和管理。** 在首页建赛时明确本机或共享球队归属；属于共享球队的比赛，从赛前到完赛持续更新同一场球队比赛。管理页不再提供第二套创建或进入记分的路径。

这是对现有“建赛即发布独立快照”默认流程的优化提案。现有本机原件、历史导入及其备份不能在迁移中被删除或悄悄改成双向覆盖。

### 4.1 新建时只选择一次归属

新建页面把“本队”明确为“比赛归属”，选项直接区分：

- WBC U12 · 本机记录
- WBC U12 · 共享球队

选择共享球队后，页面明确显示“本场会自动同步到 WBC U12，未联网的修改先保存在本机”。选择本机记录则明确显示“仅本机保存，可在赛后添加到球队”。

取消当前与本队选择相互独立的“队内共享”目标下拉框。若用户只想借用共享名单，放在次级“导入名单”操作中，不再用“选择共享球队”同时代表“仅借用名单”和“比赛归属球队”。

保存赛程与立即开赛执行相同的归属规则。比赛保存后持久保留归属，重启、改阵容、开赛和终场都不应丢失。更换归属涉及现有云端记录和成员权限，需独立复制/迁移流程，不在记分页面提供随手切换的下拉框。

### 4.2 统一入口的职责

| 位置 | 推荐入口/行为 |
| --- | --- |
| 比赛首页 | “开始新比赛”统一创建本机/共享球队比赛；“即将进行”完成赛前设置并开始，“正在进行”继续记录，“最近比赛”查看结果和进行有权限的赛后更正。 |
| 共享球队页面 | 仅查看和管理球队、名单、成员、权限、云端比赛、统计及记录核对。移除“使用共享名单开始比赛”等创建/启动入口，不增加“新增球队比赛”替代入口。 |
| 本机比赛结果 | 保留一个“添加到共享球队”入口，进入统一的添加/关联核对流程。 |
| 共享球队比赛列表与详情 | 查看赛程、比赛结果、统计和同步状态，管理观看范围、交接/记录核对等有权限事项；不放“新建”“开始比赛”“继续记分”或“更正比赛记录”编辑入口。历史档案导入属于管理既有记录，其位置与权限另行细化，不作为普通建赛/开赛流程。 |
| 已关联球队比赛的记分/结果页面 | 显示“所属球队 + 同步状态”，提供“查看球队比赛/重试同步”；不再重复要求选择共享目标。 |
| 直播与历史网页观看 | 保留各自观看授权设置，与队内比赛同步分开标注；不能把开启直播等同于上传球队比赛。 |

查看和管理可以有多个到达路径；创建、赛前设置、开始/继续记分统一在首页“比赛”中完成。共享球队页面如提供“回首页定位此比赛”，只切到首页并定位卡片，不直接启动记分或另建比赛。

### 4.3 球队比赛始终沿同一条记录继续

未来赛程 → 赛前阵容 → 开赛 → 记分 → 结束 → 赛后更正，都沿用同一比赛关联。首页提供编辑与记分，球队列表/详情提供该记录的查看与管理视图；两处读取同一比赛与状态，不再分别形成可编辑副本。首页的“即将进行/正在进行/最近比赛”按该记录的状态变化。

本机缓存负责离线保存；服务器负责共享正式版本。用户不需要在“本机原件”和“共享副本”之间手动选择才能让记分同步。已有独立原件可留作备份或单独查看，但不作为默认的第二条编辑入口。

对于先本机记录后添加到球队的场景，首次添加仍明确确认目标球队、比赛与球员对应。添加成功后默认进入关联的球队比赛；本机原件保留且标注为“添加时保留的原稿，后续不自动更新球队”。若要独立续改，应通过明确的“另存本机副本”操作，不能继续让两个外观相同的入口各自编辑且都像在同步。

### 4.3.1 首页统一启动记录（用户明确要求）

当前代码的入口并未统一：[首页列表](https://github.com/chending0418-ship-it/baseballMaster/blob/4b93361c8ce01bb1f76b23bb901a5ef177be8286/BaseballMaster/GameStore.swift#L248) 只包含没有 `sharedGameID` 的本机记录；[首页打开赛程](https://github.com/chending0418-ship-it/baseballMaster/blob/4b93361c8ce01bb1f76b23bb901a5ef177be8286/BaseballMaster/MainViews.swift#L62) 传入原本机 ID。共享正式副本的[“继续记分”](https://github.com/chending0418-ship-it/baseballMaster/blob/4b93361c8ce01bb1f76b23bb901a5ef177be8286/BaseballMaster/SharedMatchViews.swift#L342) 在共享比赛详情中，且要求 `status != .scheduled`。

因此不能简单说“共享球队比赛一定要去共享球队里开始”：现版连仍处于待开赛状态的共享副本也没有对应的开赛按钮；从首页开始的却可能是本机原件。已有代码存在两条未接通的启动/更新路径，而非产品应要求用户走不同操作。

推荐按用户要求统一为：

```text
首页“比赛” → “开始新比赛” → 选择本机球队 / 共享球队
             ↓
       同一份建赛资料
             ↓
首页“即将进行” → 同一赛前设置 → 确认阵容 → 开始记分
首页“正在进行” → 同一记分界面 → 继续记录 → 结束比赛
首页“最近比赛” → 同一比赛结果 → 统计 / 有权限时赛后更正
```

- 首页当前球队范围内能找到本机比赛和可访问的球队比赛，明确标注归属和同步状态。同一球队比赛无论从哪个页面进入，都解析到同一稳定关联；不要求返回球队管理页面。
- 对本机和共享比赛，赛前设置、确认阵容、开赛、继续与完赛的主操作一致。归属只影响保存/上传、成员可见范围和权限，不改变用户必须走的记分路径。
- 共享球队的比赛列表与首页是同一场比赛的不同视图，赛程、进行中和结束状态一致；球队列表只查看/管理，不打开赛前设置或记分界面。创建和开始/继续记录全部回到首页完成。
- 首页仅提供当前设备有权执行的记分动作。无记分权时显示查看/接手说明，仍可在比赛入口理解状态，不自动抢占他人的记分权。
- 旧数据存在本机原件与球队副本时，先保留关联、原稿与待核对内容，再确定主入口；不能仅把两个比赛卡片都放到首页，让用户继续猜该点哪一个。

### 4.4 状态、失败与统计必须可解释

| 状态 | 页面展示与动作 |
| --- | --- |
| 本机记录 | “仅本机保存”与“添加到共享球队”。 |
| 球队比赛，首次尚未上传 | “已保存在本机，待同步到 WBC U12”；提供重试，尚不能说球队成员已可见。 |
| 有后续修改未确认 | “本机修改待同步”；展示可定位的失败原因与重试入口。 |
| 服务端已确认当前修订 | “已同步”，显示最近成功时间。 |
| 无本机记分权/交接中 | 清楚显示只读、接手或交接状态，不把权限问题显示为网络失败。 |
| 资料恢复后待核对/存在冲突 | 直接引导核对，保留本机记录，不静默退出。 |

“最近比赛内容更新于”与“最近同步检查成功于”分别显示。刷新没有新内容时也应有明确结果；上传失败不能通过刷新列表成功而被遮盖。

统计范围显式区分“本机记录”和“球队已同步记录”。未同步的完成比赛必须有待同步提示和回到比赛的入口，不能只展示 0 场让用户判断为丢失。同名本机队与共享队按明确归属和 ID 关联，不按名字猜测；如本机比赛使用共享名单，也应有可选的本机记录统计范围。球队正式汇总继续以已确认的服务端版本为准，避免把未确认草稿或同场保留原稿重复累计。

## 5. 已有 0:0 云端比赛与完整本机记录的处理设计

针对旧流程，补充“补传本机完整记录到已有球队比赛”：

1. 读取已有来源关联，并对比本机/云端对阵、日期、状态、比分与修订，展示供用户核对；不按队名和 0:0 自动匹配。
2. 若云端仍是未开赛的关联赛程，且当前设备拥有有效记分权、本机内容完整，允许明确确认后更新原云端场次。
3. 写入前重读服务端版本和权限，提交仍携带并发校验；云端已有记分、其他设备接手或资料变化时转入差异核对。
4. 本机原件/补传前备份保留，失败有可重试的持久操作，重复重试不产生第二场；只有服务端确认成功才显示已补传。
5. 若只找到本机完整比赛而无来源关联，进入“添加已有比赛”；同日同对手仅提示可能重复，不自动覆盖。
6. 真实两场比赛的恢复要取得手机备份/对应记录以及授权的服务端资料后逐项核对。本提案未执行真实补传。

## 6. 实现时应满足的约束

- 保存比赛时同时保存归属、稳定的本机记录 ID、目标球队和同步状态；不能只保存在页面的临时 `@State` 中。
- 首次创建成功后建立稳定的本机 ID 与云端 ID 映射；每次编辑、开赛、完赛和更正都通过该映射更新同一云端场次。
- 创建和更新操作先持久入队再发送；重试保留同一操作 ID。保留现有 `baseRevision`、`writerEpoch` 校验和冲突草稿机制。
- 离线写入不能绕过角色或记分权。已有明确本机记分权时可离线记分；首次创建/授权尚未确认时只能显示待确认的本机草稿，不声称已拥有云端写权限或已共享成功。
- 本机原件与球队正式记录的独立保留是已有规则。迁移必须保留来源、备份及差异核对，不做按更新时间、比分或队名自动双向覆盖。
- UI 入口调整与错误诊断分别验收。“暂时连不上球队服务”不能在没有真实日志时标记为已修复。

### 9.3 推荐的实现方式与关键风险

**统一比赛关联，保留内部兼容结构。** 用户只面对一场可编辑比赛；内部可以继续保留本机工作记录、服务端已确认快照和受保护的旧原稿。增加统一的身份解析与列表/导航规则，让所有首页动作解析到同一关联，不强行把全部历史 ID 改写成一个值，也不把两个独立编辑入口继续暴露给用户。

现有 `publishedSources`、`wireLocalID`、`sharedGameID`、`acknowledgedRevisions` 可作为兼容基础，但尚不足以表达首次创建成功前的全部归属和连续修改状态。尤其当前创建操作用单独的待处理本机 ID，而用户仍可能编辑原件，需要统一识别这一阶段的“同场”关系。

**首次上传返回时不能覆盖后续记分。** 比赛保存时就持久记录目标球队、来源和待创建操作。若创建请求上传了修订 R0，用户在响应回来前又记录到 R1/R2，响应只能确认 R0；必须保留 R1/R2，再用云端 ID 和已确认修订继续更新。不能将返回的旧 0:0 快照装回当前记分界面，也不能等创建完成后才决定这场属于共享比赛。尚未确认云端记分权时应按本机待确认草稿处理，不能绕过授权声称已经共享成功。

**工作记录与队列分处不同存储，需要补偿恢复。** Core Data 保存比赛正文，共享本地状态保存持久队列和确认修订，不能假设两次写入天然构成同一个事务。需规定写入次序、保留创建意图并在重启时检测“正文已保存但未入队”或“请求已成功但响应未保存”，幂等重试并核对实际结果，避免漏传和重复创建。

**不能随意改上传正文的来源 ID。** 现有客户端把隔离副本的本机 ID 转回 `wireLocalID` 后发送；服务端更新会核对新旧 `payload.id` 一致。只把编辑入口换成云端 ID，而没有保留原来源 ID，仍会造成更新被拒绝。身份映射、活动比赛、确认修订和待处理操作必须一起核对。

**统计范围需要独立于名单来源。** 建议统计选择使用“本机记录/球队正式记录 + 球队 ID”的明确范围，而不是一个裸 UUID；同一共享名单 ID 下的本机原件和正式球队记录必须可区分。历史数据不能按队名自动并入同名本机球队。范围变更要贯通球队汇总、个人逐场、筛选、PDF 和统计去重。

**数据库格式先评估兼容，不提前决定升版。** 当前本机正文以 `StoredGame` 的 JSON 保存在 Core Data，数据库 schema 为 8，完整备份格式为 7。若现有映射能承载新规则，可避免为导航变化调整物理 schema；如确实增加持久字段，则采用明确的旧字段默认值、往返编码、备份/恢复校验和迁移测试。若新语义需要阻止旧 App 写回，必须同步评估格式保护，不能仅认为“可选字段”就一定兼容。

| 来源关联缺失、恢复后的旧授权或多份可能副本 | 标记待核对，保留记录；根据真实 ID 和权限恢复关联，不按同名球队/同日对阵静默合并。 |

实际两场比赛的恢复仍依赖完整备份与授权的云端记录。完整流程实现的工作量估计不等于已经核实、可以直接改写这两场真实数据。

### 9.6 分阶段实施与粗略工作量

以一名熟悉项目的开发者、iOS 范围、可使用 macOS/Xcode 和测试设备为前提，初步约 **7–11 人日**。这是基于静态代码影响面的工程估计，尚未实施或计时，不是交付承诺；不包含 App Store 审核、等待环境/备份/权限的时间，以及尚未定位的生产连接故障修复。若需服务端协议调整或复杂历史数据恢复，应重新估算。

| 阶段 | 交付物 | 初估人日 |
| --- | --- | --- |
| A：身份与数据方案验证 | 复核旧记录、确定归属/ID 映射和首次上传中的状态；列出迁移、备份与权限边界。 | 0.5–1 |
| B：首页与管理页入口 | 首页统一创建/赛前/记分；共享页面只查看和管理，查看不会意外进入可编辑实例。 | 1–1.5 |

### 9.7 实现验收补充

在 SF01–SF10 基础上，实施时增加以下检查，当前均未执行：

- R01：立即创建和未来赛程分别验证；首次上传未返回时连续记分甚至完赛，响应返回后本机最新内容不倒退，最终服务端只有一场且内容完整。
- R02：空共享缓存的新设备登录后，在首页发现已有球队赛程和比赛；只读成员能查看，有权设备可按同一链路开始/继续。
- R03：在正文保存后、队列保存前，以及请求成功后、响应落盘前分别中断进程，重启后不漏传、不重复建赛、不丢最新修订。
- R04：本机与共享同名、同 UUID 不同统计范围、已停用球员、跨年日期更正和旧备份恢复后，球队汇总/个人逐场/PDF 的比赛集合一致。
- R05：交接、撤权、服务恢复核对和旧端格式保护继续生效；首页新入口不能绕过既有限制。
- R06：首页完赛后回到共享管理页和 admin，核对实际状态、比分、逐球记录和最近更新；待同步时显示原因，不能仅用首页比分正确判断通过。
- R07：共享球队页面和其比赛详情没有创建、开始/继续或赛后编辑入口；管理页查看结果使用只读状态，真实编辑只能从首页进入。
- R08：本机原稿、已同步正式记录和历史副本分别保留来源，首页只显示明确的主要记录；删除或恢复任一份不会悄悄覆盖另一份。

最终放行需要实际 Xcode 编译、相关单元/集成与界面用例、至少两种设备权限以及服务端同场修订核对。静态语法检查和公网健康接口不能代替这些验收。本轮不创建或修改业务实现，不执行真实数据迁移、补传、部署或合并。
