# 球队比赛同步：问题核查与流程优化提案

记录日期：2026-11-02（北京时间）  
状态：核查与设计记录；用户已明确所有比赛均走本机创建/记录及原有本机直播，比赛结束后再选择上传到球队或仅本机保留。共享球队仅查看/管理。未指定发布版本，本轮不实施业务代码。  
核查基线：main `4b93361c8ce01bb1f76b23bb901a5ef177be8286`。

## 1. 本次需求与证据边界

用户要求先核实，再设计优化，原始反馈为：

1. 本机记录，同步共享球队，没有问题。
2. 开始设置比赛，选择共享球队，记录完毕后，没有也无法共享给球队。
3. 共享比赛的设置入口太多：建立比赛时可以设置，在共享球队内也可以设置，令人疑惑。

用户随后补充第二条的完整现象：**用第二种方式建立并记录比赛后，本队/本机球队与共享球队两个范围都看不到比赛统计，admin 后台仍显示比赛未开始。**因此本条必须作为“结束状态、统计归属和云端更新不一致”的问题记录，不能缩减成不会选择共享入口或没有另选共享目标。用户明确要求本轮先不改任何代码。

用户进一步确认：**首页“比赛 → 开始新比赛”统一创建本机比赛或共享球队比赛；设置完成后，两类比赛都从首页开始/继续记录。共享球队页面只用于查看和管理，不提供新建比赛、赛前启动或开始/继续记分入口。**此前“共享球队页面仍可作为创建或记分的快捷入口”的建议不再采用。

本次核查依据固定基线的 iOS 源码、已有测试内容及用户在 10 月 31 日提供的截图。没有取得手机完整备份、真机网络日志或生产服务器 SSH 接入；没有在本轮运行 iOS App 或重跑 XCTest。下文“代码确认”表示可以从分支条件和数据路径确定行为，不表示完成真机重现。

截至记录时，[PR #33](https://github.com/chending0418-ship-it/baseballMaster/pull/33) 仍为未合并的草稿，包含此前排查时的开赛入口、补传及错误提示修正。它不属于当前 main，也不代表用户手机已更新。本提案独立记录完整产品流程，不把该草稿视为已经发布或已通过验收的方案。

## 2. 三条反馈核查结论

| 用户反馈 | 结论 | 具体范围 |
| --- | --- | --- |
| 本机记录后共享球队正常 | 首次共享能力有代码和既有测试支持，用户也报告此路径可用；“完全没有问题”的表述应收窄 | 支持将本机比赛首次发布为球队副本，也支持历史比赛导入。但当前规则明确保留本机原件与独立球队副本，本机后续修改不会自动更新球队副本。 |
| 建赛选择共享球队，记完后两边都无统计、后台仍未开始，也无法补共享 | 完整现象有用户反馈和前述截图支持；代码存在可解释这些症状的缺口，真实记录的具体触发条件仍待核对 | 需同时核对本机完成状态/球队 ID、统计筛选、云端状态与修订。代码确认共享名单选择和共享目标独立，且已有副本会阻止重复发布；这些是候选原因，不能据此断言用户漏选了共享目标。 |
| 共享入口多且令人疑惑 | 代码确认存在多个入口，并存在文案与职责重叠 | 建赛的“队内共享”、本机比赛详情的共享、共享球队比赛列表的“共享本机比赛”、管理员的“导入历史比赛”并存。另有“使用共享名单开始比赛”，名称和所在位置容易被理解为创建球队比赛，实际仍默认保存本机。 |

因此问题不限于网络或入口数量：当前产品同时存在名单/归属语义混淆、原件/副本更新断开，以及本机记录可能落不进任何可选统计范围的代码风险。必须以“单场已结束有比分 → 对应本机范围可找到记录 → 同一云端比赛进入已结束并更新比分 → 球队正式统计纳入”为完整验收链。网络连接失败仍是独立待查事项，不能用流程结论解释所有连接报错。

### 两种代码路径与完整症状

以下路径用于解释实现及建立后续复现用例，不是对用户实际操作的替代判断。尤其“本机/共享统计都没有，后台未开始”的完整反馈不能只靠路径 A 解释。

**路径 A：只选择共享名单。** 新建 → “本队”选择 WBC U12 的共享球队 → 没有另选共享目标 → 开赛/完赛。代码预期是本机记录，不会自动上传。用户对“已经选择共享球队”的理解与实现不一致。

**路径 B：创建时已经上传。** 建赛/安排赛程 → 另选“队内共享”并上传 → 从首页打开本机赛程/比赛继续记分 → 完赛后重新选择共享球队。首次快照可能是 0:0，后续修改落在本机原件；已有副本挡住再次发布，用户既无法补传，也不知道该去编辑哪份记录。

用户截图中，本机单场显示 WBC U12 对 TOP 为 14:1，云端对应比赛仍为 0:0，并出现“查看已共享的比赛”；两个统计范围均为 0 场，用户补充 admin 仍显示未开始。用户已确认从首页“即将进行”进入。路径 B 与云端初始快照不更新相符，但它本身还不足以解释本机统计缺失；后者还需核对 E09 的归属与筛选条件。

真实记录核查应逐场对照：本机 ID、`ourTeamID`、`sharedTeamID`/`sharedGameID`、状态/`isFinal`、比赛年度与日期、来源关联、云端修订及上传队列。现无完整备份和授权的云端记录，尚不能确定是哪几个条件同时命中，也不能认定比赛已丢失或自动覆盖云端。

用户最终澄清：**本机比赛与选择共享队伍的比赛，在记录期间都走同一种本机比赛流程，直播照常使用原本机直播链路；共享只是比赛结束后的记录去向，不存在新流程中的“共享比赛内直播”。** 下文以此为当前唯一目标，替代此前持续同步、结束/移交提交以及保留两种直播入口的建议。旧版源代码和故障证据仍保留在前文用于核查，不能把旧实现的耦合当作新需求。

## 4. 最终目标：同一种本机比赛，结束后决定去向

### 4.1 用户明确的四条规则

1. 不论界面选择本机球队还是共享队伍，比赛在进行期间都创建为本机比赛，完整记录保存在本机。
2. 创建、赛前设置、确认阵容、开始、继续、结束，全部从首页“比赛”走同一条链路。
3. 记录时如需直播，照常使用现有本机比赛的文字直播；不因为预设了共享球队而切到另一套直播。
4. 只有比赛结束并保存完整记录后，才按用户的共享选择上传到球队，或继续仅保存在本机。共享球队页面只查看和管理，不创建进行中比赛，不开始/继续记分，不提供“共享比赛内直播”。

选择共享队伍表示名单来源及预设的赛后上传目标，不表示进行中已创建一份云端正式比赛。具体创建页面如何把本队与赛后去向明确表达，需沿用一次选择、清楚提示的设计，不恢复两个互不关联的共享开关。

```text
首页“开始新比赛”
      ↓
选择本机球队 / 共享队伍（共享队伍可预设赛后上传目标）
      ↓
同一种本机比赛：保存赛程 → 赛前设置 → 开始/继续记分
      ├── 用户开启直播 → 原本机直播链路正常实时展示
      ↓
结束比赛，先保存完整本机记录
      ├── 不共享 → 仅保存在本机
      └── 共享给球队 → 上传完整已结束记录 → 球队查看/统计
```

### 4.2 明确取消的旧建议

- 不再要求从共享球队页面进入独立的记分实例。
- 不在建赛、开赛或逐球记录时上传/更新球队正式比赛档案。
- 不把直播当成持续同步球队正式比赛记录的例外：直播照常传递展示资料，但它不是球队档案上传。
- 不为新流程保留“共享比赛内直播”入口，也不因共享队伍的选择切换直播协议或链接类型。
- 此前提出的“移交时上传”不作为本版默认触发条件；用户最新要求是只有结束时才上传或不上传。历史移交资料和接口的兼容另行处理，不能自行加入未结束比赛上传的规则。

### 4.3 页面职责

| 位置 | 职责 |
| --- | --- |
| 首页“开始新比赛” | 统一创建本机比赛，选择名单和赛后共享目标；不创建云端进行中副本。 |
| 首页“即将进行” | 本机赛前设置、确认阵容与开赛。 |
| 首页“正在进行” | 继续同一份本机比赛，照常记分和使用原本机直播。 |
| 首页“最近比赛”与结果页 | 查看完整本机记录和统计，按共享选择上传已结束比赛；显示赛后上传状态与失败重试。 |
| 共享球队页面 | 查看已上传比赛/统计，管理名单、成员、观看权限和档案等；不新建、开赛、继续记分或开启“共享比赛内直播”。 |

所有进行中编辑始终绑定稳定的本机比赛 ID。赛后取得云端 ID 只建立上传关联，不能换掉当前本机比赛、打断既有直播绑定或再生成另一张同场首页卡片。

## 5. 直播与球队比赛档案的边界

**直播保持原本机比赛的现有链路。** 使用现有文字直播入口、展示快照、发布绑定、实时更新、终场、关闭与有效期规则；不重做直播，也不增加“共享比赛直播”分支。

比赛的本机/共享选择不应影响 `LiveBroadcastManager` 对本机比赛的工作方式。进行中通过直播发送的展示资料只服务直播；结束后向球队提交的完整档案是另一项操作。分别显示“直播终场更新”和“球队记录上传”的结果，不能把其中一项成功当作另一项成功。

用户所说“只有结束才上传”指球队正式比赛档案，不是让已有直播停止联网。新流程验收需要同时满足：直播页面按原规则实时变化，球队正式比赛档案不在建赛/开赛/逐球时提前产生。

旧版代码里存在读取共享比赛投影的直播路径，这是历史实现，不是新方案的产品能力。实现时应让新创建比赛在记录期间始终保持本机比赛身份，继续走现有本机直播，不再进入旧共享记分/共享直播路径。旧共享直播链接和旧记录的兼容需单独评估，不能为了兼容而重新暴露新入口或直接删除旧数据。

## 6. 结束后上传的实现设计

### 6.1 先保存，后上传

1. 结束比赛时先把完整比分、逐球、状态、技术统计、名单快照、比赛时间和归属保存本机；网络异常不能阻止本机终场保存。
2. 不共享则不向球队正式档案发送记录。共享则保存目标球队、本机来源 ID、固定提交版本及操作 ID，再上传完整已结束记录。
3. 尚无云端关联时创建一次；已有来源关联时核对服务端版本和权限后更新原场次，不能因重复点击、响应丢失或更正而再建第二场。
4. 服务端确认后记录本机来源 ID 与云端 ID 的映射及已上传修订。保持本机原件不被云端旧快照覆盖，正文/投影/结束状态必须一致。
5. 失败或离线时显示“比赛已结束，本机已保存，待上传到球队”。重试同一提交，并核对未知结果，不静默停在 0:0 或误报上传成功。

赛后更正可继续保存本机；更正后的已结束比赛如何显式重新上传应在实现前细化，不引入进行中自动同步。此前终场提交已在途时，后续更正不能改变同一操作 ID 的请求正文，必须保留后续版本并区分其上传状态。

### 6.2 统计必须先在本机可查

所有本机完赛记录都应在首页结果与明确的本机统计范围可找到，包括从共享名单建立但尚未上传的比赛。球队正式汇总只统计成功上传的已结束档案。页面、个人逐场、比赛筛选和 PDF 使用一致范围，不把未上传解释成没有记录，也不重复累计同场原件和云端档案。

名单来源与统计归属需分别表示，不能仅靠球队 UUID 判断“本机/共享”范围。同名球队不自动合并；旧版使用共享名单 ID 的本机记录应有明确可查询范围。

### 6.3 旧异常记录

| 现有数据 | 处理原则 |
| --- | --- |
| 本机已完赛，无云端关联 | 原件及统计可查；用户选择共享后上传完整终场比赛。 |
| 本机完整，已关联云端仍是赛前 0:0 | 从首页结果核对后更新原云端场次，保留原稿，不再创建一场。 |
| 两边都已改动、他人有有效记分权 | 差异和权限核对，不按比分或时间自动覆盖。 |
| 只有旧云端缓存、缺本机原件或来源 | 可在球队中查看；是否建立可编辑本机副本必须有明确恢复规则，不默认把它变成新的进行中共享比赛。 |
| 恢复备份、旧授权/关联不完整 | 保留所有内容并标记待核对，不自动重放旧写入或旧移交。 |

两场真实比赛的身份和内容仍需完整备份及授权云端记录核对；本轮未执行补传或恢复。

## 7. 实现评估：复用本机记分与直播，收拢赛后提交

### 7.1 可行性

这个模型比此前“共享比赛持续同步”更集中，主要改动在 iOS 的创建归属、入口、身份判定、终场上传和统计范围。普通记分和现有本机直播作为复用基础，不重写其算法或协议；服务端原则上复用已有已结束比赛创建/更新、幂等及权限校验。

用户实际要的是本机比赛流程加赛后分发，而不是在现场维持两份可编辑比赛。因此不需要为新比赛重建一套共享开赛、连续记分同步或共享直播链路。

### 7.2 工作面

| 工作面 | 需要调整 |
| --- | --- |
| 创建与首页 | `SetupAndRosterViews.swift`、`MainViews.swift`、`GameStore.swift`：始终创建/打开本机比赛，持久保存赛后目标，完整走同一赛程/即时开赛/结束链路。 |
| 普通保存 | 本机普通编辑不再进入球队比赛上传队列；不能因使用了共享名单 ID 或预设目标而把它判定成共享工作副本。 |
| 本机直播 | 保持现有 `LiveBroadcastManager` 和本机直播绑定；新比赛不进入旧共享直播分支，终场上传球队档案不重建直播链接。 |
| 共享管理 | `TeamCollaborationViews.swift`、`SharedMatchViews.swift`：只查看/管理档案，撤出新建、开赛、继续记分及新流程的共享内直播入口。 |
| 赛后上传 | 复用完整记录编码、持久队列、来源映射、操作幂等、版本与权限校验；移除创建/普通记分触发的正式档案上传，保留明确终场提交的失败重试。 |
| 统计和 PDF | `Statistics.swift`、`StatisticsViews.swift`、`ResultsViews.swift`、`StatisticsPDFReports.swift`：本机完赛可查，球队正式档案在上传成功后计入，范围清楚且同场不重复。 |
| 存储、备份和旧记录 | 保留必要目标/来源/提交阶段；处理正文与队列分处两处存储的中断，兼容旧原稿、旧云端副本、备份恢复和 0:0 场次。 |
| 服务端 | 复用现有来源唯一性、创建/更新、`baseRevision`、`writerEpoch` 与正文/投影同次保存；不为新流程增加共享直播和进行中交接协议。 |

### 7.3 仍需验证的风险

- 结束记录可靠保存后、上传意图落盘前中断，重启后不能漏传；服务端已成功但响应未保存时，不能重复建赛。
- 服务端核对原来源 `payload.id`。取得云端 ID 后仍需保留原来源，本机记录和直播继续绑定原 ID。
- 赛后上传过程中或成功后更正，必须区分本机最新版本与已上传版本，不能用旧响应覆盖新记录。
- 用共享名单创建的本机记录不能再次落入“本机/共享统计都为 0”的筛选漏洞。
- 旧共享比赛、旧共享直播和历史移交需要兼容评估，但不能反过来扩大新流程。不能直接合并此前围绕共享副本开赛的 PR #33。
- “暂时连不上球队服务”的真实原因仍需网络/服务日志，改成赛后提交不等于连接故障已修复。

此前约 7–11 人日的粗估对应持续同步方案，随后结束/移交方案也已被当前澄清替代。当前不沿用旧工期承诺；应按“本机复用 + 赛后上传 + 统计/旧数据 + 迁移”重新估算。真实备份、既有链接兼容范围和服务器目标未核对前，不对迁移及真实数据恢复给出确定天数。

## 9. 与备案和服务器迁移的安排及未完成项

用户计划在等待备案期间整理 iOS 遗留问题，并与服务器迁移同批处理。建议同批规划、分步验证：

1. 备案等待期先核对备份与旧记录，开发并验证上述本机/直播复用和赛后提交，不执行未经核验的生产切换。
2. 在隔离目标演练数据快照、版本、域名证书、设备身份、来源映射、服务端修订、幂等记录及上传重试。
3. 生产切换采用受控的单一写入点与必要冻结，核验最后数据后再切流量；不让新旧库同时独立接受提交，不以旧库恢复覆盖新写入。
4. 尽量保持现有 HTTPS API 地址与授权连续性。如必须触发恢复代次/重新核对，明确走正式流程。迁移中的已结束本机记录可保持待上传，服务恢复后可靠提交。
5. 本机直播的服务和既有链接单独做迁移回归，不借比赛记录改版重做直播。

备案是否通过、目标主机、SSH、真实完整备份尚未核验。旧版真实连接报错与两场记录的归属/统计触发条件仍待查。本文只记录当前目标与实现评估，不修改 App/服务端代码，不合并/发布 PR #33，不执行迁移、真实补传或上线。
