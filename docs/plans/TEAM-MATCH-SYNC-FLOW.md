# 球队比赛同步：问题核查与流程优化提案

记录日期：2026-11-02（北京时间）  
状态：核查与设计记录；首页统一创建/记分、共享球队仅查看/管理的原则不变。按用户新增方案，比赛内容改为本机优先，仅结束或移交时提交；直播链路按原样保留，赛后更正与迁移细节待确认。未指定发布版本，本轮不实施业务代码。  
核查基线：main `4b93361c8ce01bb1f76b23bb901a5ef177be8286`。

## 1. 本次需求与证据边界

用户要求先核实，再设计优化，原始反馈为：

1. 本机记录，同步共享球队，没有问题。
2. 开始设置比赛，选择共享球队，记录完毕后，没有也无法共享给球队。
3. 共享比赛的设置入口太多：建立比赛时可以设置，在共享球队内也可以设置，令人疑惑。

用户随后补充第二条的完整现象：**用第二种方式建立并记录比赛后，本队/本机球队与共享球队两个范围都看不到比赛统计，admin 后台仍显示比赛未开始。**因此本条必须作为“结束状态、统计归属和云端更新不一致”的问题记录，不能缩减成不会选择共享入口或没有另选共享目标。用户明确要求本轮先不改任何代码。

用户进一步确认：**首页“比赛 → 开始新比赛”统一创建本机比赛或共享球队比赛；设置完成后，两类比赛都从首页开始/继续记录。共享球队页面只用于查看和管理，不提供新建比赛、赛前启动或开始/继续记分入口。**此前“共享球队页面仍可作为创建或记分的快捷入口”的建议不再采用。

本次核查依据固定基线的 iOS 源码、已有测试内容及用户在 10 月 31 日提供的截图。没有取得手机完整备份、真机网络日志或生产服务器 SSH 接入；没有在本轮运行 iOS App 或重跑 XCTest。下文“代码确认”表示可以从分支条件和数据路径确定行为，不表示完成真机重现。

截至记录时，[PR #33](https://github.com/chending0418-ship-it/baseballMaster/pull/33) 仍为未合并的草稿，包含此前排查时的开赛入口、补传及错误提示修正。它不属于当前 main，也不代表用户手机已更新。本提案独立记录完整产品流程，不把该草稿视为已经发布或已通过验收的方案。

## 2. 三条反馈核查结论

| 用户反馈 | 结论 | 具体范围 |
| --- | --- | --- |
| 本机记录后共享球队正常 | 首次共享能力有代码和既有测试支持，用户也报告此路径可用；“完全没有问题”的表述应收窄 | 支持将本机比赛首次发布为球队副本，也支持历史比赛导入。但当前规则明确保留本机原件与独立球队副本，本机后续修改不会自动更新球队副本。 |
| 建赛选择共享球队，记完后两边都无统计、后台仍未开始，也无法补共享 | 完整现象有用户反馈和前述截图支持；代码存在可解释这些症状的缺口，真实记录的具体触发条件仍待核对 | 需同时核对本机完成状态/球队 ID、统计筛选、云端状态与修订。代码确认共享名单选择和共享目标独立，且已有副本会阻止重复发布；这些是候选原因，不能据此断言用户漏选了共享目标。 |
| 共享入口多且令人疑惑 | 代码确认存在多个入口，并存在文案与职责重叠 | 建赛的“队内共享”、本机比赛详情的共享、共享球队比赛列表的“共享本机比赛”、管理员的“导入历史比赛”并存。另有“使用共享名单开始比赛”，名称和所在位置容易被理解为创建球队比赛，实际仍默认保存本机。 |

因此问题不限于网络或入口数量：当前产品同时存在名单/归属语义混淆、原件/副本更新断开，以及本机记录可能落不进任何可选统计范围的代码风险。必须以“单场已结束有比分 → 对应本机范围可找到记录 → 同一云端比赛进入已结束并更新比分 → 球队正式统计纳入”为完整验收链。网络连接失败仍是独立待查事项，不能用流程结论解释所有连接报错。

### 两种代码路径与完整症状

以下路径用于解释实现及建立后续复现用例，不是对用户实际操作的替代判断。尤其“本机/共享统计都没有，后台未开始”的完整反馈不能只靠路径 A 解释。

**路径 A：只选择共享名单。** 新建 → “本队”选择 WBC U12 的共享球队 → 没有另选共享目标 → 开赛/完赛。代码预期是本机记录，不会自动上传。用户对“已经选择共享球队”的理解与实现不一致。

**路径 B：创建时已经上传。** 建赛/安排赛程 → 另选“队内共享”并上传 → 从首页打开本机赛程/比赛继续记分 → 完赛后重新选择共享球队。首次快照可能是 0:0，后续修改落在本机原件；已有副本挡住再次发布，用户既无法补传，也不知道该去编辑哪份记录。

用户截图中，本机单场显示 WBC U12 对 TOP 为 14:1，云端对应比赛仍为 0:0，并出现“查看已共享的比赛”；两个统计范围均为 0 场，用户补充 admin 仍显示未开始。用户已确认从首页“即将进行”进入。路径 B 与云端初始快照不更新相符，但它本身还不足以解释本机统计缺失；后者还需核对 E09 的归属与筛选条件。

真实记录核查应逐场对照：本机 ID、`ourTeamID`、`sharedTeamID`/`sharedGameID`、状态/`isFinal`、比赛年度与日期、来源关联、云端修订及上传队列。现无完整备份和授权的云端记录，尚不能确定是哪几个条件同时命中，也不能认定比赛已丢失或自动覆盖云端。

用户最新安排：正在等待备案通过，准备将遗留 iOS 问题与服务器迁移放在同一批工作中处理；提出进一步简化——选择本机则正式比赛档案仅本机保存，选择共享则仍先保存在本机，普通比赛档案仅在结束或移交时提交。用户随后明确：直播是直播，本次只讨论共享球队下的比赛记录同步；直播链路保持不变，不能以直播为由扩大比赛记录的同步时机。下文第 4–9 节已按这一方向重写，替代此前持续同步的默认建议。备案是否通过、迁移目标和实际切换尚未核验，不能记录为已完成。

## 4. 最新方案：本机记录，结束或移交时提交

推荐将这个方案作为首阶段实现方向。它能移除逐球自动上传及其与现场记分的竞争，但仍需可靠处理整场提交、确认、重试和交接。先保存在本机不等于比赛只能从本机球队入口创建；比赛归属和记录的物理存储位置是两件事。

| 用户选择/事件 | 保存和上传规则 |
| --- | --- |
| 选择本机球队 | 正式比赛档案保存在本机，不自动提交到共享球队；主动开播仍按现有直播链路实时上传。之后主动“添加到共享球队”属于另一项明确操作，规则见下文。 |
| 选择共享球队 | 持久保存目标球队和比赛归属，正文仍先完整保存在本机；建赛、赛前设置、普通记分、暂停和重启不自动同步球队比赛记录。是否开播不改变这一归档规则。 |
| 结束共享比赛 | 先可靠保存本机完整终场记录，再提交完整正文、投影和结束状态。无云端场次则创建一次，已有移交/旧记录关联则更新原场次。 |
| 移交共享比赛 | 暂停本机记分、保存并冻结待交接版本，上传完整快照并获得确认，再完成双方确认的记分权交接；不能先显示交接成功再补上传。 |
| 上传失败 | 本机完整记录保留，显示“已结束，待提交”或“移交未完成”，允许重试同一提交；上传失败不会把本机比赛还原为未开始。 |

本轮改动对象是**共享球队下的正式比赛记录同步**：只有结束或移交才提交；是否开播不改变这一规则。直播继续按现有链路展示实时内容，直播数据上传不等于正式比赛档案提交，不作为持续同步球队比赛记录的例外。读取球队/名单/权限和主动管理操作仍各按原职责处理。

### 4.1 仍然只从首页创建和记录

首页“比赛 → 开始新比赛”统一选择本机或共享球队归属。赛程与立即开赛采用相同规则，设置完成后都从首页开始。共享球队页面仅查看和管理，不保留新建、赛前启动、继续记分或赛后编辑入口；如需要，只回首页定位比赛卡片，不直接进入编辑。

```text
首页“开始新比赛” → 选择本机 / 共享球队 → 保存到本机
                       ↓
首页“即将进行” → 赛前设置 → 确认阵容 → 开始记分
首页“正在进行” → 继续本机记录 → 结束 / 主动移交
                       ↓
本机归属：继续仅保存在本机
共享归属：结束或移交时提交完整记录，确认后标记已提交
```

同一场比赛的首页卡片、记分、结果、提交与统计通过稳定关联识别。不能因为后来获得云端 ID 就在首页多出另一场，或让用户在本机原件/共享副本之间猜测选择。

### 4.2 首页状态与云端可见范围

| 状态 | 首页展示 | 云端/队员所见 |
| --- | --- | --- |
| 本机比赛 | “仅本机保存”及正常比赛状态 | 无云端场次。 |
| 共享比赛尚未提交 | “WBC U12 · 本机记录中，结束或移交时提交” | 可能没有该场比赛；不能承诺队员已可见。 |
| 共享比赛结束、提交未成功 | “已结束 · 待提交”，可查看完整比分和逐球记录、重试提交 | 无新场次，或仍是上一次已经提交的快照。 |
| 共享比赛提交成功 | “已提交”，显示服务端确认时间 | 可查看已确认的完整比赛与正式统计。 |
| 已移交，对方继续记录 | 原设备只读，保留交接快照与归属 | 云端显示交接时快照；后续比分在下一次移交或终场提交后更新。 |
| 存在冲突、权限变化或恢复核对 | 清楚显示待核对原因和保存位置 | 保留上次正式版本，不静默覆盖。 |

因此新方案中，**共享球队正式比赛列表尚无进行中场次，或仍显示上一次交接时已提交的快照，可能是预期结果；即使直播正在实时展示，也不据此更新正式归档**；结束并提交成功后，后台必须是正确的比分和已结束状态。此前用户在旧版本发生的“已记完却两边没有统计、后台未开始”仍然是待查故障，不能用新方案倒过来解释为正常。

首页进入后台、退出记分页、定时器、普通刷新及是否开播都不能触发当前工作记录的自动归档提交。直播自己的上传与心跳按原直播职责继续，不转为球队正式比赛记录的持续提交。对已经明确触发的终场/移交提交，可以有针对该提交的持久重试；取消移交后是否继续重试必须由提交状态决定，不能恢复成逐球后台同步。

### 4.3 直播边界与待细化的提交操作

**实时直播保持不变（用户已明确）。** 不停用、不重做现有直播链路；独立直播和共享球队直播继续按原有入口、链接、实时内容、心跳、关闭和有效期规则工作。普通档案提交策略不能阻止或延迟直播必需的上传。

代码核对发现：现有共享球队直播读取共享比赛投影，并经比赛更新与 `live-heartbeat` 维护内容和时效；实现层面存在复用。**这是待隔离的技术依赖，不能据此把直播解释为实时同步球队比赛记录的例外。** 后续实现须验证如何在不改变现有直播入口、链接、实时展示和生命周期的前提下，隔离直播更新对正式球队记录的写入副作用。具体存储/提交标记或读写边界方案尚未选定，不能先承诺只改客户端即可；若需服务端兼容调整，应单列设计并在迁移评估中核验，不擅自改直播规则。

本机独立直播的临时展示资料也不等于把本机比赛加入球队正式档案。验收应分别核对直播页面的实时内容与球队正式记录的提交时间：直播照常更新，正式记录只在结束/移交改变。不能把“进行中不归档”误说成直播停止上传。

**赛后更正。** 建议更正先保存本机，通过“提交更正”主动更新云端，避免每改一条又自动上传。该操作可理解为重新提交已结束比赛，但用户尚未明确确认触发方式。需要与“本机比赛赛后添加到球队”、历史批量导入一起细化：它们都是显式提交已有记录，不应暗中变为进行中自动同步。

## 5. 结束提交和移交的实现设计

### 5.1 结束提交

1. 本机先保存完整终场版本、归属、来源 ID 和提交意图；界面立即可查看结果，不依赖网络保存成功。
2. 固定本次提交的完整内容、对应本机修订及操作 ID。不能随用户修改而改变同一操作 ID 的请求内容。
3. 没有云端关联时，复用创建接口上传完整终场比赛；已有云端关联时，复用更新接口和当前服务端修订/记分权代次。
4. 服务端确认后持久保存来源与云端 ID 的关联及确认修订；正文、投影、结束状态和技术统计必须对应同一版本。
5. 超时或响应丢失时重试同一操作或查询实际结果，不另外生成第二场。提交成功后的后续更正也不新建比赛。
6. 提交在途时如果允许更正，后续修订须另存，不能被旧响应覆盖或误标成已提交；可先采用“提交期间暂不编辑该次终场快照”的简化交互，具体体验待实施前评审。

### 5.2 移交记录

移交涉及真实记分权，不能简化成发送一份文件：

```text
首页发起移交 → 暂停本机记分 → 保存固定快照
           → 上传成功并核对服务端版本
           → 发起既有交接 → 对方读取并核对 → 对方确认接手
           → 原设备只读；接手设备从该快照在首页继续本机记录
```

- 服务端的现有提出/接受交接与 `baseRevision`、`writerEpoch`、摘要校验可复用，但要增加可靠的客户端步骤状态：提交快照成功不等于对方已接手。
- 未上传成功、未获取最新版本或对方尚未确认时，均不得显示“已移交”。收到接手请求的设备要在首页明确展示待接手及来源，不能要求去共享球队页面启动记分。
- 失败、拒绝或取消时保留原快照和有效记分权；若服务端结果未知，先查询/核对状态，再决定恢复记分，不能让两台设备同时认为自己拥有写权限。
- 接手后进行中的修改仍只保存在新设备，直到再次移交或终场；云端保留上次交接快照是本方案的明确限制。

## 6. 统计、旧记录与兼容约束

### 6.1 本机可查与球队正式统计

本机结束记录无论是否提交，都必须可从首页查看单场完整统计。统计页面显式区分“本机保存的记录”和“球队已提交的正式记录”；未提交的完整比赛在本机范围可找到，并显示待提交状态，球队正式汇总只读取服务端已确认版本。

范围不能只靠球队 UUID 推断。同一共享球队 ID 下的未提交本机记录与已提交正式版本应可区分；球员逐场、筛选和 PDF 使用一致范围。不能把未提交/被拒绝/上传中当作没有记录，也不把同场原稿和正式版本重复累计。

### 6.2 旧数据处理

| 数据情况 | 处理原则 |
| --- | --- |
| 只有本机完整比赛 | 保留正文和本机统计；是否主动添加到球队由明确操作决定。 |
| 已关联旧云端赛程仍为 0:0，本机已完赛 | 在首页结果页核对后补传同一云端场次，保留本机原件，不能再创建一场。 |
| 两边都已有记分、已被另一设备接手 | 进入差异/权限核对，不按比分或更新时间自动覆盖。 |
| 当前设备只有云端缓存 | 可查看；只有通过有效交接或当前写权限核对后，才能从首页开始/继续工作记录。 |
| 缺少来源关联、恢复后的授权待核对 | 保存全部原件，明确标注待核对，不按同名球队和同日对阵自动合并。 |

实际两场真实比赛仍需完整备份及授权云端资料核对；本轮未执行恢复或补传。

### 6.3 数据与协议

优先复用现有 `publishedSources`、`wireLocalID`、`sharedGameID`、确认修订和持久操作队列。归属和提交意图必须在首次保存时持久化，而非只存在创建页面的临时状态。

服务端更新核对原来源 `payload.id`；不能直接把正文来源 ID 换成云端 ID。界面逻辑上的同一场比赛不要求把所有历史物理 ID 强行改写成一个值。

比赛正文与共享队列目前分处不同存储。需要处理“终场正文已保存、提交意图尚未保存”及“服务端已成功、确认结果尚未保存”的中断窗口，重启后恢复明确提交，不能漏传或重复建赛。

旧备份和独立副本规则继续兼容，必要元数据采用可解释的默认值与版本保护；是否调整 Core Data schema 或备份版本须以具体落盘设计验证，不能为 UI 调整随意升版。恢复备份仍先核对权限和当前云端版本，不能自动重放过期移交或旧写入。

## 8. 与备案、遗留 iOS 问题和服务器迁移的安排

用户计划同一批处理，但建议按可核验步骤执行，避免一次同时改变 App、数据和域名：

1. **备案等待期**：整理真实记录与备份，完成 iOS 本机/结束提交/移交的开发和合成联调；记录迁移目标、域名证书、服务版本、数据/密钥/独立日志范围，当前不执行切换。
2. **迁移演练**：在隔离目标核验数据库一致快照、服务版本、访问授权、来源 ID、服务端修订及幂等结果；测试完整终场提交和移交。不能仅复制程序或使用健康检查判定成功。
3. **生产切换**：先确认备案及目标环境实际就绪，采用受控的单一写入点与短暂写入冻结完成最终数据核验，再切换流量，避免新旧服务器各自接受写入而分叉。失败时保留本机待提交记录，回退策略以保全已经接受的新数据为前提，不能恢复旧库覆盖新写入。
4. **发布与观察**：优先保持现有 HTTPS API 域名/路径和设备授权连续性；如必须换域名或触发灾备恢复核对，独立设计兼容步骤。App 更新、服务端切换分别留验收记录，同批交付不等于同一时刻一次切换。

计划迁移应核对设备凭证的服务端记录、球队访问代次、恢复代次、来源映射、操作幂等记录及旧设备授权。若采用的恢复工具会改变恢复代次/关闭访问，必须按正式恢复核对流程处理并明确提示，不能假装为无感迁移。

未取得目标服务器、可用 SSH、真实备份与域名/备案状态前，只能记录评估与检查项；本轮没有登录服务器或执行迁移。进行中不持续上传会减少切换期间的业务写入，但结束和交接仍依赖服务可用，不能视为离线即可完成云端移交。

## 9. 按新方案的实现评估（仅评估，未开工）

### 9.1 可行性与范围变化

可实现，比赛同步部分比持续上传方案更集中，主要复杂度转为明确的“整场提交”和“交接事务”，不再需要把每次现场编辑即时推送。**入口统一、统计归属、旧记录兼容和写入确认仍要完成**，不能只删除定时器。

此前约 7–11 人日的初估基于持续同步范围，不再作为本方案的当前工期；服务器迁移本来也未包含其中。直播已明确保留，但其与档案更新的耦合仍需回归；赛后更正触发方式、真实旧数据和目标服务器未确定，当前不把工作量简单按比例缩减或承诺总工期。完成这些边界核对后，再分别估算 iOS 与迁移工作。

### 9.3 分阶段建议

- **先确定边界**：直播已按用户要求保留，并核对它与共享投影更新的依赖；其余细化赛后更正、本机赛后主动添加、移交失败/取消与旧记录的处理规则。
- **实现本机与终场链路**：统一首页、持久归属、本机统计及完整终场提交，先走通 admin/正式统计确认。
- **实现可靠移交**：固定快照上传、双端确认、权限与未知结果恢复，再验证接手后继续本机记录。
- **处理旧数据和兼容**：核对来源、补传、备份/重启、统计/PDF；保留原件，不默默迁移内容。
- **演练与分步切换服务器**：迁移一致性、域名/证书、授权连续性与幂等重试验证，之后再决定部署和 App 发布顺序。

实际放行仍需 Xcode 编译、相关单元/集成、界面、至少双设备交接及合成服务端联调。新增测试优先覆盖：有无直播两种情况下，进行中均不自动提交正式档案、独立/共享直播均按原规则实时更新、终场响应丢失不重复、交接失败不双写、接手后终场更新同一场、正文/队列保存中断恢复、旧 0:0 场次补传、迁移前后未提交记录可继续提交。
