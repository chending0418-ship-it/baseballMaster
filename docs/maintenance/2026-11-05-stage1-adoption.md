## 两类映射必须分开

[归位清单](2026-11-05-stage1-path-map.json)的 `moves` 只记录既有文件去向。`docs/CURRENT.md` 对应归档快照，是保存基线原文的结果，**不是旧分支新增状态的写入目标**。同一 JSON 的 `currentContentRouting` 单独定义内容分流：

| 来自旧 CURRENT 的内容 | 新位置 | 处理方式 |
| --- | --- | --- |
| iOS 实现、版本、审核／上架及待办 | `ios/docs/CURRENT.md` | 仅迁入仍适用的增量与证据链接，保留已确认的 3.1.2 上架状态 |
| 共享球队、直播、迁移、证书等服务状态 | `ios/docs/CURRENT.md` | 简述实际阶段并链接原运维回执；服务源码仍在 live／collaboration |
| Android 实现、APK 分发、验证与待办 | `android/docs/CURRENT.md` | 仅迁入平台增量，保留已确认的 0.8.2 官网分发状态 |
| 跨平台需求与详细说明 | 根 `docs/` 下对应主题文档 | CURRENT 链接该主题；根 docs/README 只导航，不建立第三份当前状态 |
| 日期、平台或证据归属不明 | 暂存到本机保全目录待核对 | 不推定状态，不整页复制，不覆盖任何现行入口或既有归档 |

每次采用三方比较：旧分支与采用基线的共同祖先、旧分支／补丁、本轮核准的目标入口。只迁入尚未整合且仍适用的事实。合入源码、已部署、已上传、已审核与已上架分开记录；旧文档的“未上传／官网仍为 0.8.1”不能覆盖用户后续确认。

## 归档保护与旧 PR

归位清单中的 `archiveProtection` 固定记录本次修复前 94 个既有归档文件的 SHA-256，涵盖四份迁移前入口和既有原始源稿／证据。检查使用核准工作树中的摘要，不采用待合分支提供的新摘要。新增历史证据使用新的日期／来源目录，不覆盖、删除或重写这些受保护文件。

当前工作树的归档核对：

```sh
python3 scripts/validation/verify-docs-contracts.py --archive-only \
  --report output/validation/adoption/archive.json
```

在隔离整合目录可用 `git merge-tree --write-tree <核准基线> <旧PR提交>` 只读预演；它只产生临时 Git 对象，不修改分支、索引或工作树。退出码 1 表示存在冲突，输出首行为候选树对象；该树不是可直接合并的结果。用核准版本的检查器检查候选树：

```sh
python3 scripts/validation/verify-docs-contracts.py --archive-tree <候选树对象> \
  --report output/validation/adoption/incoming-archive.json
```

若提示 `protected archive changed/missing`，停止该候选结果的合入。逐文件恢复受保护归档为核准字节，把实际新增状态按上表写入新 CURRENT，再处理计划及其他冲突；不得整体采用 incoming／ours 来解决所有文档冲突。重新生成候选结果并复查，不能仅因 Git 显示“可合并”就跳过。

## 授权后的执行顺序

1. **重新保全现场。** 确认五个入口登记及两端实际 Git 根、分支和 HEAD。为两端记录索引／工作补丁、未跟踪源码与被忽略的交付证据；核对可恢复的备份和发布包摘要。盘点正在使用相关目录的构建任务，避免切换其源目录。
2. **分类未提交工作。** 逐文件判断已经进入 main、属于 #40／#42／#46／#47／#48、或仅在本机存在的内容。目前 iOS 根 3.1.0 计划还留有两项上传阶段的未提交勾选，必须随原补丁保全；采用时核对来源后转入新的 iOS 计划位置，不因迁移基线的叙述比较丢弃，也不推定为 3.1.2 的发布回执。将必要改动保存到明确的本机检查点提交／恢复分支，并保留原补丁和文件副本；只纳入已核对源码／文档，签名、缓存、原始私人资料及产物继续留在被忽略目录。处理会阻挡切换的未跟踪源码后，核对原工作区可安全切换。不使用强制切换、reset --hard、clean 或整包 stash pop。
3. **记录本次采用基线。** 独立评审及必要检查通过后，记录核准的 PR #49 完整提交 `P`，先从 `P` 在本机采用；本轮不合并 GitHub，不直接推 main。若今后先获授权合并，也可将真实合并提交作为采用基线。以下以 `A` 代表本次实际选择的核准提交，不能误写为已经进入 main。若 PR 头或 main 变化，重新审查差异。
4. **先采用 iOS／服务目录。** 在原可见 `apps/baseball-scorekeeper/` 从 `A` 建立新的 `codex/ios/adopt-stage1-<日期>` 工作分支。保留旧 `codex/dev-3.1.2` 和检查点分支。先在干净 `A` 执行完整阶段一检查，再按映射恢复真正未整合的业务增量；CURRENT 按内容分流。已合入的旧文档和资料不重新复制。关于页、上传修复、迁移／证书工具等现存改动须逐项核对归属，不能丢失，也不自动带入 main。
5. **再采用 Android 目录。** 在 `apps/baseball-scorekeeper-android/` 从同一个 `A` 建立不同的 `codex/android/adopt-stage1-<日期>` 分支；保留旧 `codex/android-0.8.2` 与检查点。按同样顺序核对干净基线、恢复未整合增量、分流 Android 状态。两个 worktree 不能同时检出同一个本地分支，不将两边都切到 main。
6. **验证每个采用结果。** 干净的 #49 采用基线使用完整检查；恢复预先保全的业务改动后，使用下面的布局模式，另对每项业务差异核对保全前字节及所属 PR。布局模式保留目录和归档约束，允许经核对恢复的原有源码及计划进度增量；不再强制迁移前的 App 字节或 3.1.0 计划正文比较，也不把原有业务增量误判为本轮新增源码，但也不替代相关 App 构建、单元／联调及业务改动的专项验证。核对 frozen fixtures、94 份归档和既有发布包；服务仅运行隔离测试和匿名健康检查，不部署、不操作真实用户记录。
7. **两端验证后再启用登记。** 在总仓库配套分支更新 projects.json 两个 active statusEntry、共享契约资源路径；更新总 README、AGENTS、总导航及引用 App CURRENT 的语音计划等有效链接。将 pending 状态更新为 locally-adopted-unmerged，记录两个实际分支、采用 SHA、未合并的 PR 和验证结果；配套检查须识别该状态，并持续校验受保护归档。以后合并再更新对应记录，不能仅改名称而沿用旧校验。正式项目路径及 Codex 五个入口不变；live／collaboration 资源路径不变。执行工作区检查，确认登记与实际文件一致。中间仅有一个目录完成时，不提前宣称两端全部采用新布局。
8. **保留恢复点。** 复核两端 HEAD、工作改动、计划及 CURRENT，记录采用结果与遗留 PR；备份和旧分支保留。两个目录均验证、登记完成且评审目录无唯一资料前，不退出评审 worktree。本流程不自动上传 App、发布 APK、部署服务或清理证据。

恢复业务工作后的布局检查：

```sh
python3 scripts/validation/verify-docs-contracts.py --layout-only \
  --report output/validation/adoption/layout.json
```

任何一步失败就保留现场和证据，停止采用该结果；使用已核验的检查点与文件副本在独立目录恢复，不覆盖正在工作的另一端。即便 #49 已合入，也可暂缓某端采用；按真实分支保留该端旧入口，记录原因与待办，不伪造已完成同步。
