## 1. 建议的产品范围

**支持对已有历史记录进行更正，先预览后续影响，再一次性保存整场修订。已经确认过的记录也可以再次更正。**

用户从局次、打席进入具体事件，查看事件发生前后局面，再修改该事件的内容。局面、比分和统计由事件变化推导；历史修改不提供脱离事件、单独覆盖总比分或总安打数的入口。

时间范围覆盖本场第一条记录到最近一条记录，不限上一球，也不受当前 30 步内存撤销栈限制。进行中和已结束比赛使用同一套编辑、预览、校验与保存逻辑；旧记录的可编辑程度由保存的信息完整性决定。

### 1.1 修改边界

| 修改内容 | 2.1 建议范围 | 保存条件与影响 |
| --- | --- | --- |
| 备注、错字、复核说明 | 支持 | 更正说明不直接改变统计；由结构化结果生成的结果名称不能只改文字来冒充另一种判定 |
| 待确认 → 正式结果；已确认结果再次修改 | 支持 | 使用统一更正流程，保留每次原值、新值与原因 |
| 安打／失误／野手选择、安打类型、牺牲打等记分认定 | 支持 | 与实际打者和跑者去向相符；重新计算所有受影响统计，包括后续关联的责任数据 |
| 守备处理、刺杀／助杀／失误责任人 | 支持 | 责任人属于当时有效防守阵容；没有可靠历史阵容信息时，不默认套用当前阵容 |
| 一次投球的坏球、看振、挥空、界外等类型 | 有条件支持 | 重新计算 B/S、投球数及自动产生的保送／三振；若改变已记录的打席边界，必须先解决冲突 |
| 一次事件中打者和跑者的上垒、进垒、出局、得分 | 有条件支持 | 逐步验证后续事件；所有后续记录仍能合法成立才允许提交 |
| 比分、出局数、棒次与当前垒况 | 随历史事件重算 | 展示变化前后结果，不允许只改合计而留下矛盾的过程 |
| 当时的打者／投手身份、换人发生时点、历史棒次重排、DH 身份 | 本版不开放直接修改 | 会改变多个事件的参赛资格、归属或棒次；既有正常现场阵容调整入口继续使用 |
| 插入漏记事件、删除事件、调整事件先后、将打席移到其他半局 | 本版不开放 | 涉及重建比赛过程，另列后续扩展；修改导致必须执行这些操作时，本次修订不能提交 |
| 比赛双方、赛季、比赛模式、预设规则、历史计时 | 不纳入本功能 | 这些属于比赛资料或规则调整，不通过历史事件编辑改变 |

守备责任更正与换人是两种操作：前者更正该次处理记给谁，后者改变从某时起谁在场。本版支持前者，不追溯改写换人顺序。姓名、号码继续沿用现有球员资料更正流程，不借历史事件编辑修改球队名单或其他比赛。

以上“有条件支持”必须在界面明确说明原因：是后续存在可修复的冲突，还是原始资料不足，或操作超出本版范围。不能只显示笼统的“修改失败”。

### 1.2 编辑单位

- 浏览单位为“局次 → 主／客队第 N 打席 → 具体事件”，保留当前主客队分别累计、跨局连续的打席编号。
- 编辑单位为一次实际记分操作。一次投球自动产生的第四坏球与保送、第三好球与三振等作为一组重新计算，不能单独编辑自动生成的一半。
- 比赛进程中的换人、换边、TB、判罚、现场修正和结束决定也要纳入后续校验，不能只检查打席内的击球记录。
- 原始事件 ID、打席 ID 保持稳定。显示编号不作为编辑定位依据；注释和修订记录不增加一次真实打席。

## 2. 修改对后续的影响

### 2.1 三种处理结果

| 结果 | 系统处理 | 用户看到的内容 |
| --- | --- | --- |
| 仅说明变化 | 更新说明与修订记录 | “比分、局面、统计不变” |
| 变化可确定 | 根据修改点之前的可靠状态，重算后续局面、统计与展示 | 涉及的打席、人员、比分、当前局面以及统计变化 |
| 存在矛盾或缺少信息 | 保留修改草稿，暂停于第一个冲突；正式比赛不变 | 冲突的局次、打席、事件、原因和处理入口 |

历史修改遵循已记录的实际行为，不能用当时的“默认建议进垒”重新猜测后续发生了什么。比如原记录是某跑者从一垒盗二垒，不能因为前面改了跑者位置，就自动换一个人或替其决定去三垒。

用户可在同一草稿内修改受影响的后续事件，每次修改重新预览，直到整个后续过程一致。修复仍受第 1 节边界约束；需要新增、删除、跨半局搬动事件或改历史阵容时，明确提示暂不支持，允许回改或取消。2.1 不提供“忽略冲突强行保存”或“清空后续记录”按钮。

即使某一处垒况重新与原记录一致，统计影响也可能继续传播，因此不能只因局面相同就停止检查责任与统计。

### 2.2 具体例子

| 原记录 → 更正 | 预期结果 |
| --- | --- |
| 一垒安打 → 失误上垒，所有人最终去向不变 | 后续实际跑垒保留；调整 H/E、个人打击和守备统计，并复核受影响的打点、失分和自责分等统计 |
| 失误责任人由游击手 → 三垒手 | 球队失误合计不重复增加；个人失误归属从前者转给后者 |
| 看振 → 挥空，均为同一次好球且不改变打席边界 | 更新该球描述及适用分类；总投球数、好球数保持一致 |
| 原记录打者停一垒 → 实际到二垒；下一条却记该打者盗二垒 | 指出下一条的起始垒位冲突，不能直接保存 |
| 原记录安全上垒 → 出局；后面又有该球员进垒或得分 | 指出后续该跑者已不存在，需要在草稿中解决 |
| 原本第二出局 → 第三出局，但同半局还有打席 | 指出半局结束冲突；不自动将后续打席搬到下一局 |
| 修正得分，使已结束比赛的胜负发生变化 | 如结束依据仍成立，更新最终比分和赛季胜负；如再见／提前结束依据发生矛盾，必须处理终场决定 |
| 旧事件只有中文文字，缺少可以确定的动作和责任数据 | 可以查看并补充说明；不能猜出一套动作去重算整场 |

### 2.3 必须同步的结果

提交后的同一修订统一驱动：逐球文字、逐打席记录、逐局比分与 R/H/E、B/S/O、垒况、当前投打及棒次、球数提醒、打击／投手／守备 Box Score、个人逐场记录、球队／球员赛季汇总、TXT、两种逐打席 PDF 和其他统计 PDF。

进行中比赛继续沿用不计入正式赛季汇总的现有口径。已结束的本队比赛更新赛季汇总；观赛和练习仍按现有规则排除。统计按修订后的比赛数据重新汇总，避免把一次更正重复累加成两场或两次贡献。

打点、自责分、第三出局计分、TB 自动跑者与换投前后责任必须有独立验收样例。不是把当条事件的安打数加减一下就完成。资料或责任计算能力不足时，明确限制该项编辑；不扩大自动计算承诺，也不在本功能中悄悄变更全 App 的记分口径。

已导出到“文件”或已经分享出去的 TXT／PDF 不会被远程替换。App 内重新导出使用最新修订，并展示最后更正时间，帮助区分旧报告。

## 3. 比赛中与赛后的使用流程

### 3.1 比赛中

入口沿用比赛记录页，并从现场记分提供清晰的“历史记录”访问路径，维持现有一屏记分布局。

1. 选择局次／打席，查看事件前后比分、B/S/O、投打及垒况，页面明确显示“正在查看历史”。
2. 点击事件的“修改记录”，按事件类型显示可编辑项，并填写更正原因。
3. 点击“预览影响”，列出直接修改、自动联动变化及需处理的冲突。
4. 冲突可在同一草稿中逐条处理；全部通过后，显示整场影响摘要。
5. 点击“保存更正”，整体保存成功后返回当前比赛；失败保留草稿并说明原因。

查看和编辑历史不自动暂停比赛计时。编辑期间使用独立页面，保存或取消后回到现场继续记分；不把历史快照写进当前正式局面。草稿若因其他操作而落后于正式比赛修订，必须重新预览，不能覆盖更新后的比赛。

2.1 首版不要求跨重启恢复未提交草稿。App 被关闭时只保留已提交版本，重新打开要明确没有保存未提交的修改；已提交更正和修订历史必须跨重启保留。

### 3.2 比赛结束后

- 从“历史比赛 → 比赛结果 → 记录”直接修改，不要求先点“恢复为进行中”。
- 一般更正保留已结束状态、实际结束时间和有效的结束原因，计时保持停止。
- 若改变得分／出局后，原结束依据不再成立，预览必须单独提示。用户可纠正为真实的结束原因；若确实还要继续比赛，则走现有“恢复为进行中”操作。不能自动补打一局、自动改变结束原因或自动恢复比赛。
- 恢复比赛属于独立明确操作；在相关更正能够形成合法状态以前，不先提交半套历史修改。因更正需要插入／删除比赛过程的情况，依第 1 节暂不开放。
- 本地更正不设“终场后一小时”的编辑限制，只要该场比赛仍保存在本机即可。

### 3.3 直播

- 先完成本地整场保存，再发布递增修订号的完整最新快照；草稿、失败保存和中间重算结果不得发布。
- 直播仍有效时，观众获得更正后的记录、比分及简短更正提示；尽量保持原展开位置。稳定 ID 避免把整场当作新记录重复追加。
- 赛后修订不改变原结束时间，不延长现有“终场后一小时”的到期时间；沿用 `live/PROTOCOL.md` 的期限规则。
- 直播已关闭或过期时，本地仍可更正，不自动重新开播；网页不因此获得永久回放能力。
- 优先复用现有修正事件和完整快照协议。若需要新公开字段，另补兼容和部署顺序；详细私人更正原因不默认加入新公开字段。

## 4. 现有实现与技术缺口

| 现有位置 | 已有能力 | 本次需要补齐 |
| --- | --- | --- |
| `Models.swift`：`ScoringEventRecord`、`GameSituationSnapshot` | 结构化事件、前后快照、稳定打席 ID | 明确操作输入、操作分组、分离参与人角色、完整重算上下文和修订记录 |
| `GameStore.swift`：`correctGameState` | 修改当前比分、局次、球数、垒况等 | 不能直接用于历史事件；需独立草稿与历史重算 |
| `reviewPendingEvent` | 仅待确认事件的一次性复核及部分统计增量 | 支持已确认事件反复更正；移除对原结果只增不减的假设 |
| `replacePendingEventSituation`、`timelineValidationError` | 验证已有前后快照衔接，冲突时拒绝 | 当前不是重新执行后续动作的引擎；不能直接开放给所有历史记录 |
| `openGame`、`commitAtomicAction`、`StoredGame.revision` | 完赛记录继续保存、事务失败回滚、递增修订及保存后直播 | 扩展为整份更正草稿、修订历史与正式比赛的一次性提交 |
| `ResultsViews.swift`、`PendingEventReviewView` | 按打席看记录、待确认补录、报告导出 | 历史局面详情、通用编辑器、影响预览与冲突定位 |
| `Statistics.swift` | 从已结束的比赛快照汇总统计 | 验证所有读取处使用同一修订，保持球队／赛季隔离 |

技术要点：

- 现有快照没有完整覆盖统计、历史守备阵容、DH、TB 责任、未决终场决定等恢复所需信息；`runnerMovements` 的去向使用展示字符串。不能把快照串联等同于完整、可重算的比赛记录。
- `secondaryPlayerID` 在不同场景承担投手或责任人角色，不能作为所有统计归属的唯一依据。新增明确的打者、投手、守备责任等角色字段，旧值只在能确定语义时迁移。
- 现有投球、击球、跑垒、换人等处理直接更新统计和日志。需要抽出共享的确定性计算层，让现场记分与历史重算使用同一规则；不能复制第二套规则长期漂移。
- 重算仅在草稿内执行，不调用会真实保存、启动计时、发送网络请求的现场方法。发生时间沿用原事件，更正时间另外保存。
- 对新记录保存足够的操作输入、实际跑者决定、第三出局计分选择、操作分组和完整检查点。已有人工修正、换人、TB 和结束决定也必须有可验证的重放方式；没有方式时作为能力边界，而非跳过。
- 结果计算与统计计算共同验证：人员与垒位合法、打席归属连续、换边／终场决定成立、统计不重复且与过程一致。边界变化不能靠改写后续快照“制造衔接”。

## 5. 旧比赛兼容、保存与撤销

### 5.1 旧比赛兼容

先建立按记录和操作类型判断的能力表，不根据“2.0／2.1”版本号一刀切。

1. **信息足够的旧记录**：根据可靠结构化字段转换，并用未修改重算结果与原比赛进行全量对照；一致后开放相应编辑。
2. **只能确定局部统计含义的旧记录**：仅开放可验证的更正；不能把未知统计清零后重新累计，也不能将局部支持标成整场可重算。
3. **缺关键状态或只有文字的旧记录**：保留阅读、原始报告及说明补充；不猜测真实打者、投手、跑者或责任。既有待确认能力须回归保留，遇到确实缺少资料的项解释限制。
4. **升级时正在进行的比赛**：可在当前可靠完整状态建立检查点，使升级后的新操作具备完整修改能力；检查点之前仍按实际资料判断，不能宣称补齐了未知历史。

开发前先确认目前 2.0 实际保存的典型比赛能支持哪些修改，并在任务 H01 交付明确覆盖表。若高频的 2.0 记录无法编辑，须反馈限制和补齐成本，不能只支持新建比赛却以“支持历史修改”验收通过。

数据结构优先考虑兼容的可选字段与显式事件格式版本。是否需要升级 Core Data Schema／备份版本，必须结合读写和旧版恢复行为决定；“JSON 能解码”不等于旧版能够安全修改新版比赛。需要升级时沿用项目现有备份、副本迁移、校验及失败恢复流程，不清库。

### 5.2 修订历史与撤销

- 每次保存保留修订 ID、基准修订、时间、原因、直接修改的事件前后内容，以及必要的恢复资料；可查看原始内容和历次更正。
- 修订记录与正式比赛一次性落盘；失败时比分、统计、历史和发布状态一起回滚。提交返回值必须反映最终持久化结果，不能仅凭校验通过就关闭编辑页。
- 一次整场更正作为一个撤销单位；不要求用户逐条撤销自动联动变化。
- 最新更正后未发生其他业务操作时，可直接撤回这次更正；有后续记分或更正时，撤回作为一份新的反向更正草稿，重新检查影响，不能用旧整场快照覆盖新记录。
- 修订历史持久化并纳入本地备份，不依赖现有 30 步内存撤销栈。撤回本身产生新的修订，发布版本号继续递增，历史不被删除。
- 现有现场撤销／重做与新增修订历史需共同设计：撤销要恢复原事件与统计，同时保留“曾发生更正／撤回”的历史事实，避免撤销栈把审计信息一起抹掉。

| H01 | 核对修改边界；盘点各事件实际保存字段、自动事件分组和旧比赛可编辑能力 | 事件覆盖表、旧比赛兼容表、关键案例的预期前后结果；先证明高频场景可做 |
| H02 | 补齐事件格式、检查点、修订历史和独立编辑草稿；确定迁移方式 | 可兼容读取、备份恢复及事务回滚的数据基础 |
| H03 | 抽取共享计算层，实现无副作用重算、完整统计更新、冲突检测和差异预览 | “不修改时等价”的重算验证；含重复更正、自动事件、换人／TB／跨局的验证 |
| H04 | 接入历史局面详情、事件编辑、后续冲突处理、保存与撤回 | 比赛中及赛后共用的一条完整交互流程 |
| H05 | 联动结果、赛季统计、导出、直播及终场状态 | App 各页面、报告和观众端使用同一修订；期限规则正确 |
| H06 | 完成回归、升级和真机体验验证，更新 2.1 发布说明 | 实际测试证据、旧数据覆盖结果和明确的剩余限制 |

按 H01 → H02 → H03 → H04 → H05 → H06 推进。H03 的引擎需要覆盖遇到的只读历史事件，不能只实现可编辑事件的计算。第一条纵向流程建议用“已确认一垒安打改为失误 → 后续跑垒保留 → 赛后统计和直播同步”，再加入改变跑垒与出局的场景。

这是对事件和统计核心流程的扩展，不能按“加一个编辑按钮”估算。工期在 H01 的资料覆盖和 H03 的计算层拆分量明确后细化；当前不承诺未验证的交付天数。

## 7. 验收场景

| 编号 | 场景 | 必须满足 |
| --- | --- | --- |
| A01 | 浏览开场至当前的历史局面 | 正确显示当时前后局面，不改变当前比赛或计时 |
| A02 | 已确认安打 → 失误 → 再改回安打 | 原统计完整恢复，无重复 PA、AB、H、E、RBI、投球或其他贡献 |
| A03 | 修改失误、刺杀或助杀责任人 | 原责任撤回，新责任正确；使用当时防守阵容 |
| A04 | 修改投球导致保送／三振条件变化 | 自动事件一起重算；不产生重复保送或三振；打席边界冲突有明确提示 |
| A05 | 更正跑者去向影响后续事件 | 定位首个冲突；草稿可逐条修复，正式比赛保持原样直至完整提交 |
| A06 | 提前第三出局、改变换边时点 | 不自动移动或删除后续打席，不将同半局已有事件继续强行执行 |
| A07 | 第三出局与得分先后、半局得分上限 | 得分有效性、逐局分和个人统计一致；保留原已确认裁判／记分决定 |
| A08 | 跨投手、代跑、重复换人、DH、TB | 正确保留身份和责任，缺少依据时明确拒绝相关编辑 |
| A09 | 普通与教练投手模式 | 各自计数和限制正确，教练模式不新增普通投手统计 |
| A10 | 完赛后修改并重启 | 仍为完赛，计时不启动；Box Score、逐场和赛季统计一致 |
| A11 | 修改后再见或其他终场依据不成立 | 明确提示并阻止不一致提交，不偷偷改变比赛状态或结束时间 |
| A12 | TXT、详细／简版逐打席 PDF、统计 PDF | 新导出与最新修订相同；单打席导出仍定位正确，旧文件不被覆盖 |
| A13 | 保存失败、取消、App 在提交前后中断 | 恢复完整旧版或完整新版，不出现过程、统计和修订历史各一半 |
| A14 | 草稿过时、连续更正、撤销／重做、跨重启撤回 | 不覆盖后续业务记录，修订号单调递增，可追溯 |
| A15 | 直播开启、断网重试、赛后有效期内修改、已过期 | 仅发布已保存完整修订，不延长期限、不重复追加、不自动重开 |
| A16 | 2.0 旧比赛、较早缺字段记录、升级中的比赛及备份恢复 | 可编辑能力与覆盖表一致，原比赛保持可读，无清零、猜测或丢失 |
| A17 | 本队、观赛、练习，多球队／多赛季 | 更正范围仅该场，赛季汇总与原隔离规则一致 |

只有计划中的支持范围通过上述相关验收，才在 2.1 更新说明中宣称可用。当前文档不新增任何“测试已通过”结论。

## 8. 建议采用的范围决定

1. 2.1 同时支持比赛中与赛后修改，不局限于待确认记录；已确认记录可再次更正。
2. 2.1 支持原事件内的内容、记分认定和可完整校验的局面修改，并可在草稿中修复已有后续事件。
3. 任意插入／删除／重排历史过程、追溯改换人或阵容暂不纳入；发生这类依赖时明确阻止本次提交。
4. 完赛更正与恢复继续比赛分开，直播到期规则保持现有口径。

若要在 2.1 同时加入漏记补录、误记删除和历史换人修复，应在实施前扩大 H01 的边界与验收矩阵，重新评估计算层与编辑流程，不默认包含。
