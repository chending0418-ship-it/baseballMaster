# BaseballMaster V1.1 按打席文字直播方案

> 范围更新（2026-09-23）：用户已接受首版文字直播方案，执行见 [V1.1 TODO](<TODO.md>)。首版固定一个发布设备，不做中途交接；球队分享暂停，因此单场发布独立建设。香港用户为主，腾讯云采购另列任务；约 50 人／场、同时不超过 5 场。下文中的设备交接和共用球队分享设施属于早期设计，不能据此扩大本轮范围。

日期：2026-09-23。范围依据用户最新说明：研究所附示例图风格的文字直播，按半局分组、按打席呈现；不做视频。本文件为设计与技术评估，尚未实现线上服务。

## 1. 建议结论

建议采用“App 继续正常记分，家长通过手机网页观看”的方案。顶部显示实时比分和局面，中部显示当前打席，下方把已完成打席整理为简洁文字卡片。每次记分自动更新，记分员不需要另外写解说。

首版使用现有服务器的 HTTPS API 和数据库；观看端约每 5 秒检查增量。比赛仍以本机记录为准，上传失败不阻塞记分。观众打开链接／二维码即可观看；私密比赛可要求访问口令。

这与 GameChanger 的非视频 GameStream 属于同类能力。其官方说明确认提供过程、比分和统计；离线记分在恢复联网后同步。这里只借鉴产品机制，不调用或抓取其比赛数据。[Viewing a GameStream](https://help.gc.com/hc/en-us/articles/360039865532-Viewing-a-GameStream)、[Offline Scorekeeping](https://help.gc.com/hc/en-us/articles/360030864752-Offline-Scorekeeping)

## 2. 观看页怎样呈现

参考图最有价值的是“一个打席一段明确的结果”，不需要为每一球生成一张主卡片。建议如下：

| 页面区域 | 内容与行为 |
| --- | --- |
| 比分栏 | 主客队、比分、当前局次、B/S/O、垒况；在实际手机观看页保持容易访问 |
| 直播状态 | 未开始／进行中／记分暂停／等待同步／已结束；注明最后收到记录的时间 |
| 当前打席 | 号码、姓名、棒次、球数、最新一条过程；每球在同一卡片内更新 |
| 已完成打席 | 半局标题 → 号码标识／可选头像 → 结果标签 → 一至两句摘要 → 结果后的出局数／得分变化 |
| 展开过程 | 点击卡片查看逐球、跑垒及守备记录，默认折叠 |
| 半局结束条 | 三出局、得分上限换边或人工结束的实际原因；不把非三出局换边显示成三出局 |
| 比赛事件 | 换投、换人、TB 放人、暂停、终场和重新开赛作为独立时间线条目，避免被过滤掉 |

首版默认使用号码圆标，直接兼容双空姓名；球员照片不作为上线前提。已确认的姓名／号码展示规则同样用于这里。

建议默认从第一局向后排列，进入直播时定位到当前半局；当前打席独立显示。用户向上读历史时，新记录不强行把页面拉走，而显示“有新记录／回到当前”。赛后继续保留同一观看链接和按局浏览。

示例文案使用已记下的事实：

- **三振**：12 号挥棒三振，1 人出局。
- **滚地出局**：陈昊击出滚地球，游击手传一垒刺杀，2 人出局。
- **四坏保送**：周子墨四坏保送上一垒。
- **一垒安打 · 得 1 分**：林宇轩击出一垒安打；周子墨回本垒得分，比分追至 2–2。
- **达到得分上限**：本半局记得 6 分，记分员确认交换攻守，实际 1 人出局。

“强劲”“穿越”“球速”等内容只有真实记录才显示。守备路线缺失时只写已确认的结果。比分追平、反超等文案可以由前后比分确定；核心过程用确定性模板生成，不需要额外的生成式 AI 服务。

## 3. 与现有实现的对应关系

当前已经具备较好的本地基础：

- `ScoringEventRecord` 保存事件 ID、局次、参与人、打席所属打者、跑者移动及前后快照。
- `GameStore.plateAppearanceRecords()` 可聚合逐球、击球、跑垒和出局。
- `PlateAppearanceRecord` 有局次、打者、完成状态、待确认状态和中文全文。
- 结果页及逐打席 PDF 已使用这些资料，名单、比分和事件不需要再录入一遍。

还需要补齐四项：

1. **稳定的打席身份。** 当前打席 ID 取聚合后的第一条事件 ID，序号由遍历生成。删除第一条事件或改变聚合后会变化，不适合作为网络更新时唯一依据。应显式持久化打席／进攻轮次 ID，与事件、修订及顺序分别存储。
2. **摘要模型。** 当前 `resultText` 直接取最后事件标题，`chineseRecord` 串起所有事件。直播需要单独生成结果标签、简短描述、得分者及结束时出局数，详细过程仍可展开。
3. **可靠发布时点。** 当前 `game` 每次变化会触发保存，复杂动作期间存在中间状态。应在一个完整记分动作成功保存后发布一次一致的比分与打席变更。
4. **持久化发布队列。** 把未发送的数据、版本和确认进度保存在本地；杀进程、重启和断网后仍能继续发送。

当前半局结束时出局数会归零，因此不能简单把事件后的 `outs = 0` 写进“本打席结果”。应显式保留事件造成的出局和半局结束原因。比分／局面展示与打席结束描述要各自使用正确时点。

## 4. 打席归属和修订边界

| 场景 | 展示和计数要求 |
| --- | --- |
| 当前打者尚未完成，跑者盗垒 | 加入当前打席过程，必要时在当前打席显示即时提示；不能给跑者再创建一个打席 |
| 跑者被抓到第三出局，打者未完成 | 显示跑者出局与半局结束；标注打席未完成，不增加该打者 PA／AB，下一轮按规则继续 |
| 达到得分上限，未满三出局 | 显示“得分上限换边”，不补三次出局 |
| 打席中途代打 | 保存该进攻轮次和参与人变化；正式打席统计归属遵循记分规则，不仅靠当前打者 ID 分组 |
| 打席间换投／暂停／TB | 独立比赛事件，按时间顺序插入，不伪造打席 |
| 待确认上垒／出局 | 显示“待确认”，不把系统建议包装成最终安打或失误 |
| 撤销上一球或上一打席 | 按稳定 ID 替换／移除原记录；比分和垒况一起回退，不能在旧记录后再追加一个负分说明就算同步完成 |
| 赛后纠正 | 原卡片更新并显示“已修订”，保留修订时间；不增加重复打席 |
| 结束后重新开赛 | 同一比赛、同一观看链接转回进行中；显示重新开赛，不复制整场 |

上述动作不要求先实现“任意历史重算”。文字直播只广播本地已经合法保存的结果；若本地编辑本身被拒绝，就没有可发布的新版本。

## 5. 记分员和观众流程

记分员在比赛页面点“开启文字直播”，确认分享范围和访问权限后生成该场观看链接。后续正常记分即可，界面只需显示“已同步／有 N 条待同步／连接中断”。可从中途开启，首次发布此前完整过程；可主动停止发布或关闭观看权限。

“停止文字直播”和“结束比赛”是两个动作。前者可以仅停止后续公开，比赛继续在本机记录；后者发布终场状态。发布停止后，观看页要明确说明数据不再更新。

观众打开链接后只读观看，不必导入球队，也没有编辑权。网页先展示最新状态和当前半局，按需加载此前半局；在微信内打开的兼容性需在真机验收，不能只测桌面浏览器。

私密链接可包含高熵随机访问令牌，也可附加口令。关闭分享后需使旧凭证失效。网址令牌不能作为第三方统计、日志或外链 Referrer 暴露；受限内容不能无鉴权地进入公共缓存。

## 6. 最小服务器设计

```mermaid
flowchart LR
    A[本地记分并保存] --> B[持久化待发送队列]
    B -->|HTTPS 发布| C[单场版本与只读投影]
    C --> D[缓存当前比分与打席]
    D -->|条件增量读取| E[手机观看网页]
```

建议与球队分享共用业务服务器、部署和身份设施，但权限分开：球队固定 16 位串码用于资料导入；单场观看链接只访问该场被允许公开的投影；发布者凭证只交给记分设备。

建议保存下列数据：

| 数据 | 核心字段／作用 |
| --- | --- |
| 直播会话 | 直播 ID、来源比赛 ID、发布者、有效发布设备、权限、发布状态 |
| 当前版本 | 单调递增 revision、最后同步时间、规则版本、比分局面 |
| 打席投影 | 稳定 ID、排序键、半局、参与人、结果标签、摘要、明细、完成／修订状态 |
| 比赛事件 | 换人、暂停、半局结束、终场等非打席事件 |
| 变更记录 | revision、更新的实体、移除的 ID，用于增量读取和补拉 |

初期一个 API 服务、关系数据库和进程内缓存即可验证，不必立即部署 Redis、消息队列集群或单独实时平台。扩展到多实例时，再提供共享缓存／发布通知或直接从数据库一致读取。

建议协议职责：

- 创建会话：上传初始比赛投影，取得发布权限和只读入口。
- 发布更新：客户端操作 ID 用于幂等，预期 revision 防止旧数据覆盖新数据；比分与卡片变更原子保存。
- 获取快照：返回截至同一 revision 的比分和已公开记录。
- 读取变化：携带上次 revision；无变化返回 304，有变化返回新增／替换／移除；历史游标太旧时要求重取快照。
- 管理会话：停播、重新发布、撤销访问、删除公开资料。

首版限制同一场只有一个有效发布设备。转交设备必须显式交接并获取新写入代次，服务器拒绝旧设备积压的迟到更新；不能仅靠两台手机“都知道串码”决定谁写入。

观看端只在前台轮询，后台降低频率或暂停，回到前台即补拉；请求失败退避重试。发布者离线期间继续本地记分，观众保留最后局面并显示等待更新；若需区分“场上很久没有动作”和“发布设备掉线”，发布者前台发送轻量心跳，不能仅凭最后一个打席时间判断掉线。

## 7. 延迟、容量和最低成本

建议首版选**约 5 秒条件增量读取**，正常网络下目标为记分操作保存后约 1–6 秒可见；这是待测目标，不是实时保证。持续推送可在需要时升级 SSE，观看页仍共用同一快照和版本协议。

5 秒轮询的容量近似如下：

| 同时观众 | 平均读取请求／秒 | 连看两小时请求数 |
| --- | --- | --- |
| 20 | 4 | 28,800 |
| 100 | 20 | 144,000 |
| 1,000 | 200 | 1,440,000 |

304 能减少正文，不能消除请求数和协议开销。后端不要每次读取都解码整场大 JSON、重新聚合所有打席，应在发布更新时产生缓存好的只读投影。

流量示例：假设每场 1,000 次实际变化、每次增量 2 KB、100 位观众全程接收，正文约 200 MB。若第一屏及初始资料各观众合计约 200 KB，增加约 20 MB；另加请求／响应头、TLS、静态资源、失败重试和历史明细。这是人为设定的估算样本，应以原型实测替换。

使用已有服务器时，最低新增工作是 HTTPS 域名／入口、数据库表、网页静态资源、鉴权、日志和备份。服务器已有余量时可能无需增加计算实例，但仍有出网及维护成本，不能承诺零费用。2 核／2–4 GB 仅作为起始压测配置；真正上线规格由并发与数据量决定。

暂不需要专业媒体服务或按视频观看分钟计费。若选择按请求收费的托管平台，要把轮询请求也纳入费用；在原有服务器上初期成本通常更容易预测，最终以实际套餐的出网额度及并发压测为准。

## 8. Apple 与资料权限

App 新增联网分享后，需要更新“仅本机保存”的隐私政策和 App Store 数据申报，按实际保存的姓名、用户内容和标识说明用途与保留期。[App Privacy Details](https://developer.apple.com/app-store/app-privacy-details/)

用户提交的队名、姓名和文字仍属于需要管理的内容，建议产品限制为比赛结构化记录并提供举报、屏蔽滥用发布者、联系方式和运营下架能力；审核需有可访问的示例比赛和后台。[App Review Guidelines 1.2、2.1](https://developer.apple.com/app-store/review/guidelines/)

如增加账号创建，需要 App 内发起删除账号及相关资料；如果不做账号，也应能停止公开及删除服务器中的比赛投影。[账号删除要求](https://developer.apple.com/support/offering-account-deletion-in-your-app/)

默认只显示所需球员资料，照片可后置；对青少年比赛，发布前应明确姓名与过程的分享范围。若用中国大陆服务器及域名，应核对所选服务商的上线条件；纯文字方案无需照搬视频服务商的推流／转码接入流程。

## 9. 建议排期与验收

先做 2–4 人日技术原型：一场示例比赛、现有记分操作驱动、手机网页观看、一次撤销与一次断网恢复。共用服务器与身份能力已具备时，含原型的首个可用版本初估 7–12 人日；正式排期以稳定打席身份和现有记分事务调整的结果为准。

验收至少覆盖：

- 当前打席多次更新始终只有一张卡片，完成后进入正确半局。
- 跑垒、第三出局、未完成打席、打席中途代打及得分上限换边没有错误的 PA／AB 或“三出局”描述。
- 比分、垒况、摘要在同一版本；没有“比分已改、卡片还旧”的混合页面。
- 撤销、重做、待确认转正式和赛后修订都更新原记录，不重复累计。
- 发布者离线、重启和重复发送后，网页最终与本地一致；旧设备不能覆盖交接后的更新。
- 观众重连、后台返回、阅读历史和快速来回切换半局时，位置及内容稳定。
- 关闭分享、失效口令、停止发布和重新开赛都有明确状态。
- Safari、微信内置浏览器及小屏真机观看；目标并发下延迟、请求量和带宽完成实测。

本轮可确认的产品方向是“自动生成摘要的按打席文字直播”。上线前还需确定典型观看人数、观看区域、私密访问方式和赛后记录保留周期。
