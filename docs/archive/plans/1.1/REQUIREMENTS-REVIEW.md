# BaseballMaster V1.1 需求评估与方案

> 范围更新（2026-09-23）：以下为前期评估记录。开发范围已由用户填写的 [确认清单](<CONFIRMATIONS.md>)收口，执行以 [V1.1 TODO](<TODO.md>)为准。球队分享、历史修改扩展暂缓；文字直播纳入；背号区分 0／00；半局超额分不计；教练规则已补充，举手杀无需额外处理。

评估日期：2026-09-23。依据：同目录《BaseballMaster V1.1 修改需求.md》、当前 Swift 源码及文末所引用的官方资料。本轮交付为需求评估和设计建议，尚未修改业务代码，也未执行构建或测试。

## 1. 结论和已确认事项

这次迭代可行，但包含三类工作：日常使用优化、记分规则与数据一致性调整、首次引入服务器的球队分享。建议按阶段验收；任意历史局面修改和文字直播先完成边界讨论与技术验证，不把所有项目同时作为首批上线条件。

用户已确认：

- 球队分享采用**导入独立副本，双方各自编辑，接收方手动再次导入更新**。
- 半局可设置得分上限，达到后**提示确认换边**，不直接自动换边。
- 直播按用户最新要求收敛为**参考所附图片的按打席文字直播，不做视频**；研究范围已确定，正式上线阶段仍待决定。此前“两种方案都研究”的选择已被本条替代。
- 举手杀规则后补，本方案不推测其具体规则。

以下写有“建议”的条目均为待讨论方案，不代表用户已经确认。

有一个发布命名问题需要提前标记：项目当前 `MARKETING_VERSION = 1.5`、Build 为 `3`，发布交接文档也是 `1.5 (3)`。本文件沿用“V1.1”作为需求名称；实际发布版本号需结合 App Store Connect 状态另外确认。

## 3. 基础体验

### 3.1 删除最后一支球队

不能只移除删除按钮的禁用条件。目前有这些实际限制：

- `SetupAndRosterViews.swift:79` 在仅剩一队时禁用删除。
- `GameStore.swift:559` 再次限制至少保留一队；初始化时空球队会回退为示例队。
- `PersistenceController.swift:99` 的加载逻辑把“没有球队但还有元数据／比赛”当作损坏；仅剩对手球队也不合法。
- `RosterSnapshot.currentTeamID` 和 `GameStore.currentTeam` 不是可空字段。
- `LocalBackup.swift:58` 的备份校验要求存在当前球队；恢复流程同样直接访问第一支球队。

建议建立合法的“没有当前球队”状态，区分首次初始化、用户删除到空、数据库损坏。初始化标记保存在数据层，不能靠数组是否为空判断是否要补 Demo。

删除建议采用下列语义：

| 数据 | 建议处理 |
| --- | --- |
| 当前球队资料与在册名单 | 从可管理球队中删除；有其他球队则切换，否则当前球队为空 |
| 已结束比赛 | 保留比赛内的球队、球员快照，仍可从历史比赛查看、导出 |
| 进行中比赛 | 保留比赛快照并允许继续；明确显示原球队已删除 |
| 未来赛程 | 保留并标记需要重新关联球队；不能假装仍可按现有名单直接开赛 |
| 旧式个人历史统计 | 建议保留在历史／归档资料入口；当前代码会随球员删除，需要调整 |
| 云端分享 | “删除本地球队”与“停止分享／删除云端资料”分别处理，确认页说明范围 |

这里“保留历史”还需要一个可发现的历史球队／归档统计入口。只保留数据库记录，但从球队筛选器无法访问，不算完成。

无球队时：首页展示“创建球队／导入球队”；统计显示空状态；本队比赛创建需先选队；有两支对手队时，观赛记录可继续使用。练习模式继续使用独立示例数据。

### 3.2 姓名、号码与排序

建议统一显示规则：有中文名则显示中文名，否则使用英文名；两者均空时显示“12 号”。保留姓名字段为空，号码回退只发生在展示层，避免以后改号码还要同步伪造的姓名。

同样规则应用到球场、跑者、换人、比赛记录、统计、VoiceOver、TXT 和 PDF。现有多处直接拼接 `#号码 姓名`，应避免出现“#12 12 号”的重复文本。

号码继续至少填一个，暂沿用现有 0–99 的整数限制。需要业务确认的细节是：

- 一人多个背号时，建议明确第一个为“主号码”，名单按主号码数值升序，其他背号仍可搜索。
- 相同号码按稳定的次级键排序，不因姓名为空而乱序；是否禁止同队重号另行确认，不能仅因取消姓名必填而自行收紧。
- 当前整数存储无法区分 `0` 与 `00`；若要支持这种区别，需单独改变号码表示。

**“按号码排列”建议只作用于球队管理、对手管理和普通选人列表。** 比赛打序和 Box Score 仍依照本场棒次；统计页继续允许用户按指标排序。不要直接重排底层球员数组来实现展示排序，因为现有默认阵容会从数组前几人生成。

旧比赛保存了球员快照，建议新增／编辑名单不追溯改写旧比赛中的姓名和号码；旧比赛渲染时同样适用空名回退。

### 3.3 Demo

首次启动说明：“已放入示例球队，方便体验；可以编辑或删除，不是你的真实球队。”示例本队和示例对手均显示标识。提示只出现一次，标识可持续显示。

建议新增明确的示例来源标记；既有用户可能已经修改示例球队，升级时不能仅凭队名相同就自动删除或重置。删除后重启、备份恢复均不补回；练习模式的示例与正式数据分开。

## 4. 半局结束、终场和重新开赛

### 4.1 分数上限与手动结束半局

比赛设置新增“每半局得分上限”：默认关闭，打开后可设 6 分等数值。达到上限后，先完整保存当前这次比赛事件及所有跑者结果，再显示“本半局已达上限，是否交换攻守？”。这应当在一次完整记分操作后检查，不能在某个跑者得分的中间状态弹窗。

建议提供“交换攻守”“继续本半局”，并在现场保留手动“结束半局”入口，覆盖裁判提前宣布换边等情况。“继续”后本半局不逐球重复弹窗，但保留达到上限的提示；撤销导致分数回到上限以下，再次达到时可以重新提醒。提示处理状态应随比赛保存，重启不丢失。

结束半局必须是一条独立事件，记录结束原因、实际出局数、实际比分和结束前后局面。**不能通过补足三次出局来换边**，否则会虚增投手局数、出局和守备数据。

需要同时处理：清空垒包、B/S/O、TB 自动跑者；正确切换攻守；保持下一棒；不额外给未完成打席增加 PA／AB。若半局在打席中途结束，下一轮应从谁继续需按赛事规则决定并写入规则测试。

分数截断规则仍待确认。例如已有 5 分，满垒本垒打后可记 9 分，也可能按赛事规定只记至 6 分。两者影响得分球员、RBI、投手失分以及本垒打结果，不能只把显示比分截成 6。

最后一局是否取消分数上限、延长局是否适用、上下半局是否同限，建议先采用“所有半局相同”这一简单设置，但须由赛事规则确认后定稿。

### 4.2 终场询问

现有 `registerOuts` 和 `evaluateWalkOff` 包含三类自动终场：

1. 达到规定局数，上半局结束且主队领先，免打下半局。
2. 达到规定局数，下半局结束且比分不相等。
3. 达到规定局数，下半局主队取得领先，再见得分。

原需求明确要求第 2 类询问“结束／继续”；第 1、3 类是否一起修改待确认。平局时也应允许记分员选择结束为平局或继续延长，不应只沿用当前自动进入延长的行为。

建议引入可持久化的“待终场决定”，避免先把比赛标为完成，再弹窗反向恢复。继续时要依据触发点处理：免打下半局的场景进入下半局；最后下半局已完则进入下一局；再见场景继续当前半局，必要时推进到下一棒。选“继续”后不得因同一个领先状态每球重复终场。

得分上限、三出局、终场条件同时发生时，只展示一个明确的决定流程，不能先换边又立刻弹第二个终场窗口。

### 4.3 明显的结束按钮与重新开赛

现场页面建议放置带文字的“结束比赛”入口，点击后选择结束原因并确认，复用现有结束原因模型。继续保持现场记分一屏可用，不挤压高频记分控件。

结果页新增“恢复为进行中”：保留同一个比赛 ID、完整比分／事件／统计／阵容，清除当前生效的结束时间和原因；计时保持暂停，由用户手动继续。增加“重新开赛”记录，保留历史结束决定供追溯。

当前 `openGame` 只负责打开比赛供查看或复核，**不会取消 `isFinal`，所以已有“打开历史比赛”不等于支持恢复继续记分**。另外，撤销栈只在内存中保存，重新打开会清空，不能用现有撤销代替正式恢复功能。

对自动终场恢复，必须保留结束触发时所处的阶段。当前三出局终场前会清空局面，再见终场分支也可能提前返回而未推进打者；单纯设置 `isFinal = false` 会造成错误棒次或重复半局。新版本需保存终场检查点；旧比赛缺少资料时让用户核对恢复局面，不猜测。

赛季统计目前只纳入已结束比赛，因此恢复后该场会暂时从正式统计中移出；再次结束后重新计入一次。结果页应明确提示这一变化。分享过的比赛再次结束或复核后，发布者需要主动发布更新；已经生成的 PDF 和接收方的旧副本不会自动改写。

## 5. 球队分享建议方案

### 5.1 产品选择：发布快照，导入副本，手动更新

建议 V1.1 采用一个明确流程：

1. A 在球队详情点“分享球队”，选择历史比赛／赛季范围，并包含当前名单和未来赛程。
2. 上传前预览将分享的人数、比赛数、赛程数及资料范围。
3. 首次成功发布时服务器分配固定 16 位串码，后续发布只增加版本。
4. B 输入串码，看到球队名、更新时间和数据量，确认后导入本地独立副本。
5. B 可离线查看、编辑和继续记录自己的比赛；这些操作不会回写 A。
6. A 后续修改后点“发布更新”；B 点“检查更新”，预览新增、变更、删除和冲突，再确认导入。

```mermaid
flowchart LR
    A[A 的本地球队] -->|主动发布版本| S[服务器上的球队快照]
    S -->|串码查询与预览| B[B 的独立本地副本]
    S -->|B 手动检查更新| D[比较上次导入与双方变化]
    D -->|确认后合并| B
```

这是按球队交换资料的功能。现有 `.bmbackup` 是整机替换恢复，不能直接用来导入，否则会覆盖 B 的其他球队。

### 5.2 串码与权限

建议服务器为每个发布的球队实体生成随机 16 位数字，数据库设置唯一约束，冲突时重试；以字符串传输和保存，保留前导零，也避免 JavaScript 数值精度问题。界面可按 `1234 5678 9012 3456` 分组，支持复制粘贴与二维码。离线新建球队先有本地 UUID，联网首次发布后才分配正式串码。

这里的“每队唯一”应指**一个发布实体**，不能靠队名判断同一现实球队。A 的串码作为 B 副本的“来源串码”保留；若 B 将独立副本另行发布，它是新的发布实体，获得自己的串码，不能覆盖 A。是否开放接收方再次分享建议作为独立开关。

16 位串码只定位球队，不能同时作为管理密码。发布、修改、关闭和删除云端资料需独立授权。建议首版使用轻量发布者身份：设备安全保存管理凭证，另有可离线保存的恢复凭证；也可以改为发布者登录，取决于是否需要跨设备管理。普通本地记分不要求账号。

不可修改的串码应配套“停止分享”，停止后仍占用原码，不分配给其他队。恢复分享可沿用原码；管理凭证可撤销／更换。若仅凭串码即可读取，泄露后重新开放仍会被原持码者访问，因此建议支持可更换的访问口令；对私密球队采用串码加口令，管理凭证始终独立。

关闭分享只能阻止后续读取，不能收回对方已导入的离线副本，发布前应明确这一点。恢复管理权的材料不得放入公开分享包，也不应明文混入现有未加密的普通备份。

### 5.3 分享哪些数据

| 包含 | 建议边界 |
| --- | --- |
| 球队资料、在册名单 | 包含稳定来源 ID、姓名与全部号码；不附带接收方设备偏好 |
| 选择范围内的历史比赛 | 以完整单场快照包含双方参赛名单、规则、比分、事件和三类统计，便于核对和 PDF 导出 |
| 未来赛程 | 包含时间、对手、规则及已有阵容，并导入所需的最小对手资料 |
| 赛季信息 | 保留来源赛季身份及名称，避免不同来源同名赛季误合并 |
| 来源和版本 | 分享包格式版本、发布球队 ID、修订号、生成时间、校验摘要 |
| 旧式个人记录 | 若选择分享，作为独立类型保留原统计范围，不能假装完整比赛 |

默认不发布进行中比赛，也不上传该设备所有无关对手球队和个人资料。实时比分是另一条会话式发布流程，不通过不断发布整个球队包实现。历史比赛中的对手快照属于完整比赛资料，但不应自动复制对手所有当前赛程。

### 5.4 再次导入怎样处理冲突

保存“来源 ID → 本地 ID”的映射、上次导入的来源版本，以及可比较的基线。原始 UUID 不能直接当作所有设备之间共享的本地身份：同一副本再次导入要识别为更新，不同来源碰撞或再次转发也不能串队。

| 相比上次导入 | 默认建议 |
| --- | --- |
| A、B 都未改变 | 跳过 |
| A 改了，B 没改 | 预览为更新，确认后采用 A 的新版本 |
| B 改了，A 没改 | 保留 B 的修改 |
| A、B 都改了且结果不同 | 显示冲突，由 B 选择保留本地或使用来源 |
| A 新增记录 | 新增导入；同一来源记录不重复累计 |
| A 删除记录 | 显示来源删除，不直接删除 B 的资料；B 可确认移除 |
| B 新增记录 | 保留，与 A 的资料并存 |
| B 删除了来源记录 | 保留本地删除标记；再次导入不无提示复活，A 同时修改时列出冲突 |

首版冲突粒度建议为“单个球员资料／单条赛程／整场比赛”。**同一场比赛按整场选版本，不能自动拼接双方的逐球事件。** 当选择替换时，预览说明会替换哪些本地修改，并可先导出本地版本。

球队名单移除球员时，保留该球员在既有比赛里的快照；B 新增比赛引用 A 的某个球员时，来源删除不能破坏 B 的比赛。赛程已在 B 处开打或结束后，A 的时间修改或删除必须作为冲突处理，不能降回未来赛程。

统计方面，导入比赛快照后由现有统计层聚合，不能再把分享包中的赛季合计另加一次。若一场现实比赛由两个独立发布者各自记分，它们的来源 ID 不同，系统只可提示疑似重复，不可仅按队名／日期强行合并。

### 5.5 实现和服务器

建议组成：HTTPS API、关系数据库保存身份／串码／版本／清单、对象存储保存压缩的版本化球队包。版本包先上传完整并校验，再原子更新“当前发布版本”，避免接收方拿到半份资料。旧包按保留策略清理。

客户端导入采用“下载 → 格式与引用校验 → 差异预览 → 建立回滚点 → 事务合并 → 重算统计”。失败时整批回滚。来源映射、导入基线和删除标记纳入本地备份，但不包含发布管理密钥。

技术接口可先按这几个职责拆分：创建发布实体、上传新版本、按串码读取清单、下载指定版本、停止分享、删除云端内容、恢复管理权。写操作带幂等键和预期版本，读接口限流并限制包大小；日志不记录管理凭证。

初期可使用已有服务器承载 API；单实例加数据库与备份足以开展小规模验证。2 核／2–4 GB 可作为压测起点，不是生产容量保证。是否另用对象存储、可保留多少历史版本，以实际单队数据量、球队数及下载量决定。即便已有服务器，备份、出网、监控和域名仍需计入运维成本。

发布者换机建议优先恢复身份后沿用原发布实体。仅有普通球队备份但没有管理凭证，不应直接取得原串码的写权限。恢复凭证丢失后的找回方式、是否引入账号，是开发分享功能前需要确认的产品决定。

## 6. 修改历史局面：可行性与边界

当前有结构化事件和局面快照，能作为后续基础，但并非完整的可重放事件系统：

- `reviewPendingEvent` 只允许修改仍为待确认的事件；统计修正按特定结果增量处理。
- `replacePendingEventSituation` 修改待确认事件的后局面后，会检查它与后续快照是否衔接。
- `timelineValidationError` 主要比较相邻快照并校验有效性，没有执行所有历史动作并重新计算整场统计。
- 局面快照没有包含完整的历史阵容、每项统计、全部投手责任和规则状态；部分事件字段还以展示字符串表示位置。

因此不能把限制改成“所有记录可编辑”就宣称支持任意历史修改；反复用目前的一次性统计补正路径可能造成重复累加。

建议分三档：

| 档位 | 示例与承诺 | 建议 |
| --- | --- | --- |
| A：说明修订 | 备注、描述文字，不改变事实、参与人和统计 | 最先可做，保留修订历史 |
| B：局面不变的记分纠正 | 跑者、得分、出局、棒次和换人完全相同，仅纠正部分结果归类／责任 | 可作为首版，但需建立白名单和可靠的旧值撤回、新值应用机制 |
| C：会改变后续状态的修改 | 出局改上垒、换打者、改得分、插入／删除球、改换人或投手 | 独立重算项目，先验证数据是否足够，不列为低成本小改 |

“安打改失误”虽然垒况可能不变，也可能影响后续自责分和投手责任，不能一概归入安全小修改；自动跑者、继承跑者等记录亦需整段核对。旧数据缺少必要资料时，应明确拒绝相关修改或只允许追加说明。

建议首版做 A，加上经过样例证明可可靠重算的 B；赛中和赛后使用同一修订流程。保持已结束状态的赛后修订与“恢复为进行中”是两个不同动作。

C 档若后续立项，最低需要：版本化事件命令、完整检查点、确定性重算、规则版本、修订前后差异预览、首个冲突定位、事务保存与撤回。例：二局一垒跑者后来盗二垒，把早先上垒改为出局后，盗垒事件会引用不存在的跑者。系统应指出冲突并要求修正后续记录，不能静默编造一个新过程。

退回某一历史节点并丢弃其后记录也是一种实现，但会删除后续数据，不能当作“单独修改局面”的等价替代。若要提供，需作为明确的重录功能另行确认。

## 7. 教练投手模式

建议把规则模式放在 `GameRules` 中，与已有“本队比赛／观赛”和“立即开赛／未来安排”分别表达。旧比赛缺失模式字段时按普通比赛解码；开始比赛后不随意切换模式，避免一场比赛内混用统计口径。

必须拆开两个概念：

- P 位球员：属于双方球员名单，参与棒次，正常获得刺杀、助杀、失误等守备数据。
- 实际投球者：教练角色，不生成球员投手记录；是否记录姓名和实际投球次数是可选产品项。

现有 `currentPitcher` 总会返回一位球员；投球、保送、安打、失分、三振等路径直接更新这位球员的投手统计。因此要修改数据层和记分路径，不能只隐藏投手统计页面。

建议范围包括：规则选择、赛前阵容、场上对位文案、换人菜单、各种投球／跑垒／判罚路径、赛后复核、单场与赛季统计、TXT/PDF、导入与备份。教练投手场次的投手栏应显示“不适用”，普通模式的其他比赛仍正常计入个人投手统计。统计总览提供按模式筛选，避免不同规则的打击数据未经说明就作同口径比较。

还需取得这些赛事规则，不能从“教练投手”名称推断：是否四坏保送、触身球如何处理、每打席投球数上限、两好球后的界外、三振条件、盗垒／暴投／捕逸是否适用，以及 DH／大谷条款如何处理。建议这一模式默认不启用 DH／大谷条款，待规则确认。

举手杀暂保留在需求中，正式产品不放无功能的开关。规则补充时需要明确触发者、触发时机、死球／活球、打者是否出局、跑者回垒或进垒、得分有效性、守备统计归属，以及与分数上限的优先顺序。规则影响打击结束和跑垒处理，未补齐前不能声称完整教练投手模式已验收。

## 8. 按打席文字直播研究

用户提供的参考图采用半局标题、球员标识、结果标签和简短事件描述。建议在这个结构上增加置顶实时比分和当前打席，已完成打席按半局分组，点击展开逐球及跑垒过程；得分、换边、待确认和修订有明确标记。

推荐首版：**现有 App 记分 → 保存后主动发布 → 手机网页只读观看**。一场比赛一个发布来源，观众打开链接或二维码即可查看；发布权与只读观看权限分开，球队 16 位串码不能自动赋予某场直播的写权限。

已有 `plateAppearanceRecords()` 和 `PlateAppearanceRecord` 可复用聚合思路。正式直播还需稳定的打席 ID、完整操作提交后的发布队列、版本与删除标记、断网补传及观看端差异更新。现有 `resultText = events.last?.title` 不能直接满足“简洁结果摘要”的全部情况。

首版建议 HTTPS 发布加约 5 秒一次的条件增量读取，服务端缓存最新局面，未变化时返回 304。后续按连接量和延迟需要升级 SSE。比分和打席记录按同一个版本更新，撤销／修订替换原卡片，不能作为新打席重复追加。

服务器可与球队分享共用 API、数据库、HTTPS 和运维设施；文字流量主要取决于事件数、单次更新大小、观看人数和轮询频率。无需视频推流、转码或录像存储费用。100 人观看两小时、每 5 秒读取一次，约 14.4 万次请求；若全场 1,000 次实际变更、每次增量 2 KB，增量正文约 200 MB，另加首次加载与协议开销。以上为容量示例，不是实测或云服务报价。

GameChanger 官方明确 GameStream 提供比赛过程、比分和统计，独立于视频；其离线记分完成后可在联网时同步。可借鉴这个发布与恢复方式。参见 [Viewing a GameStream](https://help.gc.com/hc/en-us/articles/360039865532-Viewing-a-GameStream)、[Offline Scorekeeping](https://help.gc.com/hc/en-us/articles/360030864752-Offline-Scorekeeping)。

Apple 相关工作集中在联网数据隐私、用户提交内容的处置及可用审核入口。球队名称／姓名／记录上传后，原先“仅本机保存”的声明需更新；如果引入账号创建，需要 App 内发起账号删除。参见 [App Privacy Details](https://developer.apple.com/app-store/app-privacy-details/)、[审核指南](https://developer.apple.com/app-store/review/guidelines/)、[账号删除](https://developer.apple.com/support/offering-account-deletion-in-your-app/)。

具体页面结构、事件归属、同步协议、费用模型和验收要求见 [按打席文字直播方案](<LIVE-BROADCAST-PLAN.md>)。

## 9. 技术依赖与实施顺序

第一阶段先把空球队、姓名显示、排序和 Demo 做完整；这些工作能独立验收。第二阶段集中处理半局结束、终场决定和重新开赛，避免在几个按钮中分别堆叠不同的换边逻辑。教练投手规则明确后接入同一套状态转换。

第三阶段实现球队包与本地导入，再接服务器发布和手动更新。先证明“导入后数据与统计一致、重复导入不重复计数”，再增加网络传输，减少问题来源。

历史局面任意修改会改变比赛数据格式，分享格式必须有明确版本；实时比分也需要广播修订。建议共同保存规则版本、比赛修订号和来源身份，但不为了未来可能出现的功能提前做多人协作平台。

数据库当前为 Core Data V2、备份格式 V1；新字段不能仅更新 Swift 模型而忽略旧 JSON 解码。应增加兼容默认值、必要的 Schema／备份格式版本，并覆盖 V1/V2 数据与旧备份导入。新备份若包含旧版无法理解的语义，应让旧版明确拒绝，而不是静默丢字段。

当前 `GameStore.game` 的每次属性变化都可能持久化整场。对于换边、导入和历史修订，建议先在临时状态完成整项操作，校验后一次提交，避免中途状态进入数据库或网络发布队列。

## 10. 验收重点

| 功能 | 必须验证的场景 |
| --- | --- |
| 空球队 | 删最后一队、重启、导出／恢复空队备份、只有对手球队、保留历史、进行中比赛继续、未来赛程重新关联 |

| 终场与恢复 | 三类终场条件、平局、选继续、手动结束后重启恢复、再见后棒次、计时暂停、赛季统计只计一次 |

以下为熟悉现有项目的一名工程师、需求已确定、正常验证资源可用时的初步工程量，包含相关开发与回归，不是交付日期；不含 Apple 审核等待、外部账号开通及举手杀规则等待。

| 工作包 | 参考工程量 | 前提 |
| --- | --- | --- |
| 基础体验四项及空数据兼容 | 3–5 人日 | 确定历史保留及主号码规则 |
| 半局上限、终场询问、重新开赛 | 5–9 人日 | 确定达限计分与三类终场行为 |
| 教练投手基础模式 | 4–8 人日 | 投球与跑垒规则齐全；举手杀另估 |
| 球队分享，含独立副本及冲突预览 | 10–18 人日 | 服务器环境、身份恢复与分享范围确定 |
| 受限历史修订 A＋可验证 B | 5–10 人日 | 编辑白名单及旧数据范围明确 |
| 任意历史修改 C | 暂不承诺 | 先做 2–4 人日数据与重算原型，再估算 |
| 按打席文字直播原型 | 2–4 人日 | 基础服务器与单场身份已就绪，验证发布与观看 |
| 按打席文字直播可用版本 | 7–12 人日 | 含 App 发布、网页观看、修订／弱网恢复与相关验证；共用身份设施已就绪，包含前述原型 |

已确认的三项选择见第 1 节。接下来影响实现的主要问题为：

1. 达到分数上限的同一次击球产生超额分数时，全计还是截断？最后一局／延长局是否同限？
2. 主队免打下半局、再见得分是否也改成询问结束／继续？
3. 一人多号码是否以第一个为主号码排序；排序范围是否采用本方案的名单／棒次区分？
4. 删除球队是否采用“删除名单但保留比赛及历史入口”，未来赛程保留并重新关联？
5. 分享管理采用设备管理凭证加恢复材料，还是发布者账号；是否需要私密口令和接收方再次分享？
6. 历史修改首批最常见的 3–5 个实际错误是什么？据此决定 A／B 的白名单。
7. 文字直播目标区域、典型观众数、月比赛数和赛后文字记录保留周期分别是多少？这决定服务商和预算。

建议先定稿基础体验与比赛状态规则，球队分享按本文件的快照方案继续细化；举手杀、任意历史修改和直播分别保留自己的验收边界。
