# Android 首页本机比赛与共享名单来源（2026-11-02）

按现行计划第 15.3 节收拢安卓流程；只修改 Android，不修改 Swift、共享协议或服务，不连接生产服务验证。

## 本轮实现

- 首页「开始新比赛」始终进入同一赛前设置。没有本机球队时仍可明确读取共享球队名单，不强制先造本机球队。
- 赛前选择本机球队或显式刷新、选择共享球队。共享读取通过现有授权核对及名册接口；只读取，保存独立名单快照，不向共享名册回写。
- 比赛内球队使用共享球队稳定 ID，球员保留 `sourceID`，保留共享球队、成员、名册修订及 `sourceID → rosterID` 来源映射。映射是来源资料，不是授权，不包含 token。
- 共享快照不插入本机可编辑球队库；若共享身份撞上已存本机球队，独立保存事务拒绝并保留原资料。不能通过更改 `source="local"` 绕过旧约束。
- 共同流程依旧是确认双方阵容、开始／安排、记分、继续、结束；本机 ID 不因名单来源改变。直播复用现有 `AndroidLive` 与本机比赛 ID。
- 共享比赛页只看比赛、历史和管理观看设置。旧进行中共享直播保留已有链接和明确关闭入口，移除新开启入口；旧权限、记录、待处理请求和前台旧直播保活保持，不自动建赛或补传。
- 结束继续使用事务保存完整本机比赛。共享名册来源不代表已经上传档案。

## 验证入口

`SharedRosterLocalGameTest`：共享名单比赛的离线记球→撤销／重做→终场→备份恢复；错误保存入口、撞号不覆盖；提交前失败全事务回滚。

## 完整来源终场档案的提交基础

本轮继续实现受限的 `FinalArchiveSubmission`，实际 App API 为 `AndroidTeamSharing.stageFinalArchive(backupID, gameID, teamID, confirmed)`、`previewFinalArchive`、`sendFinalArchive`。输入从 Room 读取已校验的完整原始来源备份，不接受原生内部 Game JSON 或尚未完成的 wire prototype。

- 只允许完整重放核对通过、终场、有结束时间的来源比赛；只允许球员原身份与当前共享名册 `sourceID` 一致的子集。其余映射明确拒绝，原文件和本机比赛保留。
- 使用现行服务 `history-imports/preview → commit`，保留原 source ID，固定独立远端副本 ID。副本 ID 不改变本机比赛 ID 或直播绑定。
- 先将完整请求快照、source digest、本机修订、稳定 operation ID、成员及访问／恢复代次持久保存，再做显式预览；没有自动提交入口。预览已有来源不进入 commit；相似比赛必须明确独立场次确认。
- 预览通过后固定 commit body，超时／丢响应／进程重启续取同一请求，不重新造 ID 或快照。权限／访问／服务恢复代次改变保留请求并禁止发送；旧共享绑定和 0:0 场次不被自动覆盖。
- 回执仅确认所发本机修订，保存于现有 AES-GCM／AtomicFile 协作私有文件。代码不安装服务器 payload、不替换本机 Game，因此旧回执不会覆盖新的本机更正。普通 `.bmandroid` 不恢复这些共享请求或权限。

测试增加 `TeamDirectoryIntegrationTest` 四项，复用真实现行 Node/SQLite 服务、回环动态端口及合成数据，覆盖磁盘序列化重启、成功提交后丢响应的同请求续取／唯一场次、代次改变阻止 commit、401 将旧意图归档隔离、请求写盘失败不调用导入服务；`TeamDirectoryFileTest` 增加加密持久请求及失败恢复检查。测试执行结果按本轮统一日志登记。

这仍是受限来源档案的 API 与提交基础：尚未接入终场上传产品界面；尚不接受原生新比赛、不同球员身份映射、已关联旧场更新、明确冲突重传与全量统计去重。不能据此将 AN05 完整赛后上传勾选为完成。

球员关联严格沿用服务：`playerLinks.targetID` 指向名册球员的 **sourceID**，不是编辑名册行的 `id`。本子集发送显式 identity links，服务 `normalizeLinks` 会移除 sourceID==targetID 的恒等映射；省略后的统计仍按原球员 ID 归属。隔离测试核对原始玩家 ID、名册 sourceID 和服务正式 box 统计一致，并确认丢响应重试只产生一个正式档案。尚未实现不同身份的交互映射或跨本机／共享统计去重，所以不将完整球队统计验收写成通过。

访问权改变、401、重连或服务恢复时，旧终场意图／回执保留在 `PreservedRecoveryWork` 并从活动队列隔离；再次选择同来源不会新建请求绕过核对。旧请求正文不自动生成新 operation ID 或新代次。

本机统计选择器同时纳入这些共享名单快照比赛，明确显示「本机共享名单记录」和「不代表已上传球队正式档案」。同一球队的多场快照按稳定球员 ID 合并，较新快照优先展示队名／球员名，历史出现而新名单中已无的球员仍保留，避免年度记录失去入口。该合并不会改写名册库或声称云端正式统计去重已完成。

补记临时球员仍允许留在本机比赛，原共享来源映射保持，未关联的新球员不自动发明共享身份；需要上传时另行核对。`LocalMatchSourceTest` 覆盖上述快照合并与补记名单的历史预览。

2026-11-02 本机 `core-verification-2` 构建成功：现行真实协作服务隔离回归 **67 项，0 失败／错误／跳过**，其中本记录新增的四项完整来源终场提交测试均通过。直播隔离服务 **8 项**、显式 Swift session **1 项聚合**通过；Swift 聚合不能当作真实 iOS App／Core Data 验收。
