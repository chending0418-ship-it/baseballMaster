## 实现

- 新增共享球队详情、完整名册、成员与邀请列表读取，名单／球队资料 PATCH、成员角色／移除 PATCH、邀请撤销 DELETE。沿用现行服务，不改 iOS／服务端／协议；三名管理员与最后管理员保护由原服务决定。
- `SharedRosterPlayer` 同时保留云端 `id` 与比赛所用来源 `sourceID`；不按姓名、英文名或背号合并。保留空背号、停用状态等服务可读事实；需要转为安卓新比赛快照时对空姓名／空背号明确拒绝，不补造。可读档案最多 2000 人，现役最多 200 人，背号字符串区分 `0`／`00`。
- 从本机球队明确创建共享队时，先冻结有效本机名单和来源 ID，再与 operationID、恢复秘密、待绑定本机 ID 一起加密落盘。云端另分配球队／球员 ID；成功回执与绑定同一次本机存储提交。失败重试保留同一请求，不能重复创建。当前只发送有效本机球队的现役名单，不发送比赛、历史、停用本机球员或设备授权。
- 共享名册在独立加密缓存保存，供新比赛使用的 `Team(source="shared")` 是分离快照；不写入／覆盖原有 Room 本机球队。云端球队 ID 与来源球员 ID 对应保持稳定；原本机名字、名单、比赛和备份保持独立。
- 读取名册前刷新权限目录，只在球队修订变化时重新下载；下载后再次刷新，核对数据库恢复代次、成员身份、角色、球队访问代次与名单修订。读取过程中变化则拒绝该次结果，不把过期响应作为现值。成功的旧幂等回执也不能降低较新缓存版本。
- 成员变为不可访问、成员身份／访问代次变化、数据库恢复代次变化时，移除可用共享名册及绑定；失效／非管理员的邀请和恢复秘密不继续作为活动资料保留。401 清理活动目录缓存，不生成新凭证、不恢复旧授权。**未确认请求不因撤权而丢弃**，保留原文并由服务器拒绝；不能借刷新或新建操作绕过。
- 名单和成员修改保留 baseRevision。`409 roster_conflict` 等明确版本／规则拒绝保留原操作和错误码；提供显式“保留拒绝请求为草稿”API，归档原请求后才能按新预览／新编号重新准备。未知网络结果、401／403／404、操作编号冲突不能通过该 API 清空重做。不会自动采用新版本或覆盖服务端。
- `AndroidTeamSharing` 提供 IO 协程应用接口，从真实 GameRepository 读取本机球队并准备发布；目前仍未接产品共享菜单。准备不联网，发送单独显式执行。Room schema／普通业务备份不为协作凭证增加字段。
