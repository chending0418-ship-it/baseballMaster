# GameChanger 历史数据迁移可行性

调研日期：2026-09-18。目标：将新版 GameChanger 的棒球历史数据迁入 BaseballMaster。用户已确认使用新版；球队 Staff 权限、赛季数量和真实导出文件尚未确认。本次完成官方文档核查和本地代码审查，未登录用户账号、未执行数据迁移，也未实现导入功能。

**结论：历史统计迁移可行，推荐以官方 CSV 为入口，配合原始 Scorebook PDF 存档。完整逐球过程的无损迁移目前不能承诺。** 官方导出能力已确认，但具体字段覆盖和转换准确率仍须用真实样本验证。

## 1. 官方数据出口

| 出口 | 已确认的能力 | 对迁移的意义 |
| --- | --- | --- |
| Stats → Export Stats | 新版 App 和网页均支持 CSV；仅球队 Staff 可导出；导出遵循当前比赛筛选条件 | 主要入口，可保留赛季总计；筛选单场可逐场收集统计 |
| Plays → Scorebook → 分享 | 棒球／垒球 Staff 可查看并分享本队单场记分册 PDF | 适合保存原始比赛凭证；若要变成可计算事件，另需解析和核对 |
| Box Score 导出 | 官方列出棒球／垒球 iOS 导出入口 | 可补充单场核对资料；不应假设与统计 CSV 同格式 |
| Export XML | 仅指定为 College 的棒球／垒球队 Staff，网页按单场导出 | 符合条件时另行评估；不能作为普通青少年球队默认方案 |

依据：[Exporting Season Stats](https://help.gc.com/hc/en-us/articles/360043583651-Exporting-Season-Stats)、[Stat Filters](https://help.gc.com/hc/en-us/articles/360043142972-Stat-Filters)、[View Scorebook](https://help.gc.com/hc/en-us/articles/360058035392-View-Scorebook)、[Print Options](https://help.gc.com/hc/en-us/articles/360058489071-Print-Options-in-GameChanger)、[College XML Export](https://help.gc.com/hc/en-us/articles/24581262301453-XML-Export-College-Teams-Only)。

导出权限取决于球队角色。普通关注者即使能查看部分统计，也不能据此认定有导出权限；可以由现有 Staff 导出文件后交给迁移者。

官方帮助未给出完整 CSV 字段规范或稳定版本契约，因此暂不保证某一份文件同时包含全部打击、投手、守备数据、双方名单、日期、逐局比分或稳定的球员／比赛 ID。第一步必须检查原始文件，缺什么再补什么。

本次在官方产品与帮助资料中未找到面向一般第三方开发者的公开数据 API、OAuth 或全量账号导出契约。这是检索结果，不等于证明不存在商业合作接口。当前不应把“输入账号后一键同步全部历史”列为已确认可实现的功能。

官方条款第 3.2、3.4 节限制向第三方共享账号密码、自动化访问和商业抓取。产品路线应优先采用用户主动导出的文件；需要直连同步时，再取得官方支持的接入方式。[GameChanger Terms of Use](https://gc.com/terms)

另外，设置中的 Send Packaged Data 是把设备数据上传给 GameChanger 客服排障，并非已确认的可下载完整备份入口。[Packaging Your App’s Data](https://help.gc.com/hc/en-us/articles/360050080551-Packaging-Your-App-s-Data)

## 2. 能迁移到什么程度

以下是根据导出入口与本项目结构作出的工程判断，尚未经用户真实文件验证。

| 目标 | 可行性 | 边界 |
| --- | --- | --- |
| 球员与赛季基础信息 | 高，依赖文件内容及少量手工补全 | 姓名、背号可用于辅助匹配，但不能作为永久唯一标识；完整名单未必都在统计文件中 |
| 历史赛季总计 | 高 | 保留文件中已有原始计数；不能从赛季合计还原逐场成绩 |
| 球员逐场统计 | 较高，导出工作量随比赛数增加 | 每场单独筛选导出；日期、对手、主客场、比分等缺失信息需要另行补充 |
| 历史战绩与逐局比分 | 有条件可行 | 要有实际赛果和逐局数据；不能从球员打击统计猜测对手得分或分配各局得分 |
| 原始记分册查看 | 高 | 将 PDF 关联到历史比赛；BaseballMaster 需要新增附件持久化与查看入口 |
| 每球、换人、跑垒的可编辑重放 | 未验证，复杂度高 | CSV 总计不包含事件顺序；PDF／可取得的逐球文字可辅助重建，但不等于完整事件数据库 |
| 视频、消息、照片、关注关系 | 当前方案不覆盖 | 统计出口无法证明能迁移这些内容；需要独立调查导出权限、文件和产品承载方式 |

大学队 XML 值得作为单独扩展，但官方说明只足以确认其比赛统计导出能力，不能在未看样本前承诺可还原 BaseballMaster 的全部逐球状态。

## 3. BaseballMaster 已具备的基础和缺口

已核查本地 Swift 源码，以下判断不依赖网页推测。

| 现有实现 | 意义／需要改动 |
| --- | --- |
| `Models.swift:110` 的 `BattingLine` | 已有 PA、AB、H、长打、RBI、BB、HBP、SO、SB 等基础计数，可复用统计概念 |
| `Models.swift:332` 的 `PitchingLine` | 已有出局数、失分、自责分、保送、用球数等；IP 应转换成出局数，不能直接当普通小数 |
| `Models.swift:351` 的 `FieldingLine` | 已有 PO、A、E、DP；文件没有提供的项目需要表示为未知 |
| `Models.swift:165` 的 `PlayerGameRecord` | 仅包含个人打击记录，缺少独立投手／守备统计及导入来源，不够承载完整导入 |
| `Statistics.swift:189`、`:200` | 球队赛季总览只统计已完成的本队 `StoredGame`；塞入旧式个人记录不会自动进入球队总览 |
| `Models.swift:1030` 的 `GameState`、`LocalBackup.swift:58` 起 | 现场比赛模型和校验需要双方名单、打序、逐局比分等；不能为了通过校验制造虚构历史比赛 |
| `GameStore.swift:3480` 的 `restoreBackup` | `.bmbackup` 恢复会替换本机数据；外部导入需要合并、去重、预览和撤销，不能直接复用恢复流程 |
| `PersistenceController.swift:45`、`LocalBackup.swift:12` | 当前数据库 V2、备份格式 V1；新增持久化内容需要同步处理兼容、备份与恢复 |

两个会影响统计一致性的具体问题：

1. **牺牲打分类。** 当前 `BattingLine.sacrifices` 合并 SH 和 SF，`GameStore.swift:1043` 也将两者累计到同一字段；OBP 分母使用这个合计。标准 OBP 对 SH、SF 的处理不同，导入模型应分别保存，旧记录不能在缺少事件依据时强行拆分。[MLB OBP 定义](https://www.mlb.com/glossary/standard-stats/on-base-percentage)
2. **ERA 口径。** `PitchingLine.era` 固定按 7 局计算。导入应保存 ER 和出局数，同时核对原数据的 ERA 基准；不能仅复制显示比率，也不能假设两边采用相同口径。

## 4. 推荐实现方式

建议新增独立的历史统计记录层，再让统计页统一读取本地记分和导入记录。不要把一个赛季总计伪装成一场比赛。

导入记录至少需要包含：来源、导入批次、文件摘要、球队／赛季／球员映射、统计范围（整季／指定比赛）、字段可用性、原始计数、原始文件和可选附件。有源系统 ID 就保存；没有时由导入预览确认本地对应关系。

建议的用户流程：

1. 选择 GameChanger 导出的一个或多个文件。
2. 指定所属球队、赛季，以及“赛季汇总”还是“单场统计”。
3. 匹配球员，预览新增／更新／疑似重复记录及缺失字段。
4. 核对总数与关键计数，确认后合并保存。
5. 在统计页标注 GameChanger 来源；缺少的项目显示“未提供”，原始 PDF 可单独查看。

实现时必须处理的细节：

- **球员匹配：** 姓名、背号、赛季共同辅助匹配，支持中文名与英文名对应；同名、改名、换背号需要人工确认。当前背号保存为整数，`00` 与 `0` 等源数据差异需要保留原文后再决定映射。
- **缺失值：** 缺少投球数与投球数为零是两种情况，不能把缺列自动当零；由缺失字段计算的比率也应标记不可用。
- **IP：** `5.2` 表示 17 个出局数；`5.2 + 0.1` 应累计为 `6.0`。若实际导出采用其他表示法，依据样本转换。
- **比率：** AVG、OBP、SLG、OPS、ERA、WHIP 应由有效原始计数重算，并保存源显示值供核对；不要平均多个比赛的比率。
- **字段语义：** BB 与 IBB 是否包含关系、SO 别名、分区表头、合计行、练习赛筛选均需样本确认。总计行不能当球员再次求和。
- **去重：** 文件摘要只解决完全相同文件；重新导出的修正版还需按球队／赛季／比赛和球员匹配，提示替换而非累计。
- **范围重叠：** 同一赛季总计与其逐场记录不能同时相加。只有明确互斥的覆盖范围才能合并；整季汇总不能参与“近 3 场”筛选，也不能把每人的出场次数相加当成球队比赛数。
- **未知比赛信息：** 没有比分时不推断胜负，没有逐局信息时不构造逐局比分，没有事件时不开放依赖事件重放的赛后修正。
- **文件兼容：** 按表头和分区识别 CSV，处理 BOM、引号、姓名中的逗号、换行、空值和字符编码；未知列保留在原始资料中。
- **数据恢复：** 导入前备份；保存应完整成功或整体回滚；新增历史记录和附件需要纳入后续 `.bmbackup` 导出及恢复。

## 5. 首轮验证需要的最小样本

先取同一支球队的一个旧赛季，准备：

1. 一份未经表格软件改写的完整赛季 CSV，并记录当时的筛选条件。
2. 两到三场比赛各自筛选导出的 CSV，覆盖普通比赛、换投和牺牲打等情况。
3. 对应比赛的 Scorebook PDF；如果 iOS 可导出 Box Score，也一并留存。
4. 这些比赛的日期、对手、主客场和最终比分，用来核对 CSV 是否已包含这些元数据。

导出路径：App 中进入球队 → Stats → Export Stats；需要单场时，先在 Filter Stats 只选择该场。也可以在 [GameChanger 网页](https://web.gc.com) 中使用对应 Stats、Filter Stats 和 Export Stats 入口。具体权限和功能依据见第 1 节。

验证通过的标准：

- 可说明每个目标字段的来源、缺失情况和转换规则。
- 选定比赛的球员计数与源文件一致；IP 按出局数完全一致。
- 比率差异可归因于舍入或已明确的口径，并在预览中说明。
- 重复导入不会再次累计；修正版可以受控替换。
- 赛季总计与单场记录不会重叠计入；缺失值不会变成虚假的零。
- 导入后重启、导出备份和恢复备份均保留同一批数据与附件。

## 6. 范围与工作量判断

以下仅为初步工程估算，前提是取得稳定 CSV 样本、单人熟悉现有 Swift 项目，不包含等待文件或人工逐场导出时间：

| 阶段 | 交付内容 | 粗略工作量 |
| --- | --- | --- |
| 样本验证 | 字段清单、差异报告、转换小样，不接入正式数据库 | 1–2 个工作日 |
| 可用的统计导入版本 | 球员匹配、整季／单场记录、去重、统计页适配、备份兼容与必要验证 | 约 1–2 周；拿到样本后重新估算 |
| 原始记分册附件 | 关联、查看、删除和备份恢复 | 在统计版本基础上约 1–3 个工作日，视附件存储设计调整 |
| 逐球过程重建 | 文字／PDF／可用 XML 的解析、复杂事件映射及逐场核对 | 暂不承诺排期，先验证原始资料是否足够 |

目前适合立项的是“导入 GameChanger 历史统计”。是否扩展到完整比赛过程，应由真实样本的覆盖率决定。下一步最有价值的是取得一个赛季 CSV、两到三场单场 CSV 和对应 PDF，完成字段级验证，再确定最终开发范围。
